## PITCH 1 (Primary): Goal-Defined Agent Loops — Replace the Fixed Pipeline Sequence with a Verifiable Goal State and Retry Logic

**Technique:** Stop treating your agent pipeline as a fixed sequence of steps and start treating it as a loop toward a verifiable goal. The distinction: a script executes predetermined steps in order and fails if any step breaks; a loop defines a terminal condition ("episode passes QC") and retries adaptively when partial failures occur — re-running only the failing beat, not the whole episode. This is what Boris Cherny (Claude Code's creator at Anthropic) meant when he said he "stopped prompting Claude" and now only writes loops. The technique requires two things and only two: a trigger (launchd schedule) and a verifiable goal (QC PASS). Everything in between becomes adaptive.

**Why it matters for us:**

Kyle's current `generate-episode.sh` pipeline is a fixed 5-step sequence: ingest → build-pitch → 2-pass write → QC → render/mix/publish. The critical failure mode is silent underperformance: when QC fails or a beat comes up thin, the pipeline either stops outright or continues producing a weaker episode. There is no mechanism to go back to the specific failing beat and retry it.

Every day's run produces a QC verdict (the `step3-qc.txt` and `step4-qc.txt` files exist in `.tmp/`). That verdict already identifies which sections failed. The missing piece: wiring that verdict back to a retry of only the problem section.

With a goal-defined loop:
- **Thin beat**: the loop goes back to that beat's reporter agent with a "sources came up short — try X, Y, Z alternate sources" prompt rather than publishing a half-baked segment
- **QC fail on voice/dedup**: the loop identifies the specific violation and rewrites that beat only, not the whole episode
- **Source drought days**: the loop runs ingest twice with different parameters rather than silently producing a thin show

This is the gap between a pipeline that *executes* and a system that *delivers*. Kyle's pipeline already has all the primitives: launchd as the trigger, QC PASS as the verifiable goal, beat agents as the retry units, `.tmp/` as external state. The only missing piece is the loop wrapper that wires the QC verdict back to a targeted retry.

**Build sketch** (an agent could run this cold from this file):

1. **Define the goal state in generate-episode.sh**: after the 2-pass write, run QC. Parse the QC output for `QC VERDICT: PASS` vs. `FAIL`. If PASS, proceed. If FAIL, enter the retry loop.

2. **Parse which beat failed**: the `/qc-episode` output already names the failing sections. Extract the beat ID from the QC output (e.g., "sports segment — dedup violation on NBA Finals" → beat ID: `nba_sports`). This can be a simple grep/awk on `step3-qc.txt`.

3. **Retry only that beat**: re-invoke the failing beat's reporter agent with the QC feedback as additional context: "Previous run failed QC for this reason: [extracted failure reason]. Research fresh sources and rewrite only this beat." Save to the same beat output slot.

4. **Reassemble and re-run QC**: feed the fresh beat into `/assemble-episode` for splicing, then QC again.

5. **Set an exit condition**: max 2 retries per beat, max 3 QC passes total. After that, fail loudly (write `EPISODE_FAILED.txt` with a full trace) rather than silently publishing a substandard show. This is the "loop termination" Loopcraft requires.

6. **Log the retry**: write retry events to `.tmp/loop-trace-YYYY-MM-DD.txt` so future sessions can see how often specific beats fail and which sources triggered retries. This is the "external state" primitive — the loop gets smarter over time because it can read its own history.

## What I looked at and discarded

**HarnessX / AEGIS (arxiv 2606.14249, June 12)** — Real academic paper (14 authors, Tingyang Chen et al.) with credible benchmark results: +14.5% average gain across ALFWorld, GAIA, WebShop, tau³-Bench, and SWE-bench Verified, up to +44% on weak baselines. AEGIS is a four-stage trace-driven evolution engine (Digester → Planner → Evolver → Critic) that reads production traces and proposes harness changes, testing them in isolated git worktrees. There's an open-source implementation (harness-evolver by raphaelchristi, v6.4.2 as of April 2026). **Why it didn't clear the bar for today's pitch:** The open-source implementation has 28 GitHub stars and requires a LangSmith API key — it's academically credible but hasn't crossed into practitioner adoption yet. The paper benchmarks are on ML task-solving agents, not media production pipelines, and the applicability to Kyle's setup requires more inference than I'm comfortable pitching without a practitioner who has actually run it on a comparable pipeline. Worth watching: if harness-evolver gains traction or a practitioner runs it on a production content pipeline with published results, this becomes a strong future pitch. Especially the `harness:evolve` command pattern (reads failed runs, proposes changes to CLAUDE.md and context docs) maps directly onto Kyle's daily pipeline traces.

**Claude Code v2.1.179 (released June 16)** — Pure bug fixes: mid-stream connection drop handling, WSL2 mouse-wheel scrolling fix, sandbox glob performance, feedback survey fix, subagent navigation fixes. No new features, no new primitives, nothing to build on. Passing.

**Fable 5 ban coverage (IndyDevDan, Cole Medin, Matthew Berman — multiple videos, June 12-16)** — News, not technique. The ban is genuinely disruptive but the actionable harness-engineering content in the IndyDevDan Fable 5 video was already mined for the June 16 model-tier routing pitch. The Cole Medin and Matthew Berman ban coverage is reaction and analysis, not a buildable technique.
