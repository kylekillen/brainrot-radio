## Pitch 1 — Claude Code sessions can now message each other natively (v2.1.224); it's a first-party, better-tested replacement for the exact IPC layer that's been breaking all week

**Technique.** As of Claude Code v2.1.224 (shipped 2026-08-07, two days ago), any two
*live* Claude Code sessions — interactive or headless `claude -p` — can exchange short
text messages directly, with no extra infrastructure. Two new tools: `ListAgents`
(discover reachable sessions) and `SendMessage` (deliver to one by name). Same-machine
delivery travels over a per-session local Unix socket and never touches Anthropic's
servers; cross-machine delivery is reply-only, routed through Remote Control. It's a
message-passing primitive, not a session merge — no conversation history or files
cross over, only text — and it's already available with nothing to enable once a
session is on 2.1.224+ on macOS or Linux.

**Who's doing it.**
- Anthropic, official docs: [code.claude.com/docs/en/cross-session-messaging](https://code.claude.com/docs/en/cross-session-messaging)
  and the version 2.1.224 changelog entry at
  [code.claude.com/docs/en/changelog](https://code.claude.com/docs/en/changelog)
  ("Added cross-session `SendMessage`: Claude Code sessions can now message each
  other, on any of your machines, with `ListAgents` to discover them").
- Independently reported within 24-48h by seven unrelated outlets, all converging on
  identical mechanics (same version number, same tool names, same permission-hold
  behavior — no contradictions found anywhere):
  [9to5Mac](https://9to5mac.com/2026/08/07/claude-code-now-lets-sessions-talk-to-each-other-on-macos/),
  [MacRumors](https://www.macrumors.com/2026/08/08/claude-code-adds-cross-session-messaging/),
  [DevelopersIO / Classmethod](https://dev.classmethod.jp/en/articles/20260807-cc-updates-v2-1-224/),
  [Claude Hub (FR)](https://www.claudehub.fr/en/blog/claude-code-2-1-224-cross-session-messaging-sandbox-fix/),
  [Clauding.de](https://clauding.de/en/posts/claude-code-2-1-224-self-hosted-runner),
  [Glitchwire](https://glitchwire.com/news/claude-code-sessions-can-now-message-each-other-context-handoff-just-got-simpler/),
  [AI Weekly](https://aiweekly.co/alerts/claude-code-v21224-lets-sessions-message-each-other-on-macos-and-linux).

**Evidence it's real.** Read the full official docs page directly, not just the
changelog blurb, and confirmed the mechanics that matter for a headless fleet:
- **Headless `claude -p` sessions bind an inbox socket and can receive messages**,
  same as interactive ones — unless started in "bare mode," which skips the socket.
  This is the critical fact for a fleet built almost entirely on `claude -p` daemons
  and role workspaces.
- **Unattended delivery to a headless worker isn't automatic.** A `-p` session can't
  show the approval dialog a held message needs, so a message just sits held forever
  unless that session's `--settings` explicitly sets `crossSessionInbound: accept`.
  Worse: Claude Code's *default* holds every message for approval when the receiving
  session runs with bypassed permissions (which most of this fleet's autonomous roles
  do) — meaning turning this on naively, without setting `accept`, would silently
  recreate the "nobody's there to approve it" failure mode this fleet already knows
  well from the burn-stop/task-dispatcher pause. That's a real gotcha the docs state
  plainly, not a hidden trap I found the hard way.
- Independent write-ups from outlets with no connection to each other all describe
  identical tool names, identical version, identical hold/deliver/refuse semantics —
  convergent corroboration, not one blogger repeating a press release.
- Checked whether this is already in use anywhere in the fleet: `grep -rl
  "SendMessage\|ListAgents\|cross-session" ~/observer-system` turns up nothing in the
  actual coordination code — only unrelated wiki mentions of an unrelated "cross-
  session" concept in `dreaming-the-mechanism.md`. The fleet's `agent-msg.sh` /
  `wake_role.py` / `role_mail_router.py` stack predates this feature and doesn't use
  it. Genuinely unadopted, not a rediscovery of something already built.

**Need it serves.** Priority 2 — multi-agent AI businesses, specifically "the unlock
... shifting from single-thread human-AI work to multi-agent collaboration ... without
his constant attention." It's not hypothetical: `~/fleet-optimizer/STATUS.md`'s last
two weeks document real, recurring bugs in the *live-session-to-live-session* half of
the fleet's homegrown mail path — a void-delivery hole that let a verified defect
report sit unread for hours, an `iris_seen` field that's referenced in a comment but
never set anywhere in the actual code, a positional-argument mis-parse that silently
dropped a whole message body, a routing rule that misrouted whenever a re-spawned
agent reused a previous agent's name. Every one of those is precisely the class of bug
a first-party, Anthropic-maintained transport is built and tested to not have — for
the specific case where both parties are already running, which is most of the
COS-to-Fleet-Optimizer, Lead-to-reviewer, and parallel-worktree-worker traffic that
happens *during* an active work session.

**Whole-fleet leverage.** Cross-cutting, not project-specific: every live-session-to-
live-session handoff anywhere in the fleet is a migration candidate. It does **not**
replace the tickler/INBOX-file path used to wake a dormant or dead role — native
messaging only works when the target session is already alive and has bound a socket
— so this is additive to the existing system, not a rip-and-replace. That's actually
the right shape: it takes the "both sides are live right now" traffic off the fragile
custom mail router without touching the harder dead-role-resurrection problem the
fleet already has a purpose-built (if imperfect) mechanism for.

**Build sketch.**
1. Read `scripts/agent-msg.sh`, `observer/coordination/__init__.py` (`wake_role.py`),
   and `role_mail_router.py` in `~/observer-system` and classify the fleet's existing
   role-to-role message types into two buckets: "recipient may be dead" (keep on the
   tickler/INBOX path — no change) vs. "recipient is reliably alive during this
   exchange" (candidate for native `SendMessage`).
2. Pilot on exactly one low-risk pair from the second bucket — e.g. COS → Fleet
   Optimizer status pings, or a code-reviewer replying to the author that opened its
   PR — since both sides are typically running concurrently during a work session.
3. Explicitly set `crossSessionInbound: accept` in the piloted roles' settings before
   relying on it — do not assume default behavior, since the fleet's autonomous roles
   mostly run under bypassed-permission modes where the default *holds* every
   incoming message for Kyle's approval, defeating the entire point.
4. Verify with `/list-agents` (or `/status` → `Peer address`) that the target role's
   session actually binds an inbox socket — confirm it wasn't launched in bare mode —
   before wiring any real traffic through it.
5. Leave the existing tickler/INBOX file path fully in place as the fallback for
   dormant/dead recipients; this is a targeted addition to one failure-prone slice of
   the coordination layer, not a system rewrite.

**Status: pitched.**
