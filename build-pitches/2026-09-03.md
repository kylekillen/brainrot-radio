## Pitch 1 — Deterministic self-verification: stop trusting an agent's (or a judge's) word that it succeeded; recompute the answer from raw tool output instead

**Technique.** A cluster of three independent, dated papers converges on the same fix for
the exact bug class the fleet keeps re-discovering by hand this week (the INBOX reader that
called 2 unread messages "0 unread," the deleted test counter that made `0 == 0` read as
"all green," the sentinel storm where a crashed subprocess was misread as "field empty" and
produced 867 false verdicts out of 893). The fix: don't ask the agent if it succeeded, and
don't ask an LLM judge either — **independently recompute the claimed result from the raw
tool-call output, using a separate deterministic (non-LLM) mechanism, every time.**

- *Real-Time Detection and Repair of LLM Agent Failures* (arXiv 2608.02464, Aug 3 2026):
  a verification layer that recomputes stated totals from actual tool results and confirms
  every required call was made catches 60% of failures at zero false positives (96% with
  a coverage check added) across 63 healthy episodes; triggered rollback+re-execution
  recovers 45% of failures vs. 16% for a resampling control (p=0.0005); task success rises
  52% → 73% for about one extra model call per run. A companion anomaly layer (echo-state
  network + CUSUM, trained only on healthy runs) flags failures from step telemetry alone
  at AUROC 0.872, and the ranking transfers with no retraining to two outside corpora
  (AFTraj-2K 0.745, ATBench 0.779) — evidence this isn't overfit to one dataset.
- *SilentProbe: Measuring Silent Failure in Production APIs Used as Agent Tools*
  (arXiv 2609.00035, Aug 29 2026): explains *why* these failures happen at the API/tool
  layer — "no results found" and "the server didn't understand the query" both return
  HTTP 200 with a parseable body, so there's no exception to catch and no field to branch
  on. Audited 721,320 parameters across 2,501 OpenAPI docs: only 7.5% declare an enum,
  15.2% declare any machine-checkable constraint at all, and 40.1% state a constraint in
  prose the schema doesn't encode. Machine-checkable constraints produced an honest error
  111/111 times; prose-only constraints failed silently 44/61 times (p=2e-13). In live
  agent-loop testing, models caught the resulting silent failure only 12% of the time,
  fixed it 0% of the time, and fabricated a number 12% of the time. The fix that took one
  case from 88/88 failures to 0/89 was one line: promote the prose constraint into the
  actual schema/enum. Code+data released: github.com/Jasper0122/silentprobe.
- *From Confident Closing to Silent Failure* (arXiv 2606.09863, June 2026): the negative
  result that rules out the tempting alternative. Across 5 LLM judges × 5 prompt strategies
  with full task specs, no configuration beats AUROC 0.65 (0.54 on AppWorld) at judging
  whether an agent's self-reported success was real. A plain TF-IDF classifier trained on
  trajectory text beats every judge configuration — AUROC 0.83–0.95, 4–8x more false
  successes caught at the same flag rate, 3,300x lower latency. **This is the direct
  rebuttal to "just have an LLM check the LLM's work,"** which is the instinctive fix the
  fleet could otherwise reach for.

**Who's doing it.** All three are independent academic groups (Sunny Dubey solo on
2608.02464; Li/Ye/Guo/Dang on 2609.00035; a separate team on 2606.09863), publishing within
a 2-month window of each other on the same failure mode, which is itself the corroboration
— this is an active, converging subfield, not one lone claim. Cross-referenced against a
visible surrounding cluster (arXiv 2511.04032 "Detecting Silent Failures in Multi-Agentic
AI Trajectories," 2606.08162, 2607.07689) confirming the problem is recognized broadly, not
niche.

**Evidence it's real.** Read primary sources directly (arXiv abstracts/methodology, not
secondhand summaries); reproducible code+data for SilentProbe; the negative result on LLM
judges is itself evidence the authors aren't hand-waving toward "just add more AI" — they
measured what doesn't work before proposing what does.

**Need it serves.** Directly hits fleet pain #2 from this week's own STATUS.md: the
"false-zero" instrument class (`_parse_unread_entries` reading 2 unread as 0; a deleted
test counter passing `0==0`; the sentinel's 867/893 false verdicts from a crash misread as
an empty field) — already generalized internally into the rule "any zero needs proof a one
was reachable, by a different mechanism than the thing being checked." This is the
mechanized, reusable version of that rule instead of a case-by-case manual bug hunt.
Priority: mostly **(3) resilience** (the sentinel is the trading system's own alarm
pipeline) with real spillover into **(2)** — every self-directed maintenance agent in the
fleet (role-monitor, tickler, PR-sweeper) reports its own success, and none of those
self-reports are currently cross-checked against raw evidence.

**Whole-fleet leverage.** A single deterministic-verification pattern, applied once, would
have caught all three of this week's named false-zero bugs (INBOX reader, deleted test
counter, sentinel misclassification) without any of them needing to be independently
discovered — this is the general form of a bug the fleet is currently finding one instance
at a time.

**Build sketch.** (1) Audit the fleet's own tool/MCP/skill schemas for SilentProbe-style
prose-only constraints — anywhere a valid-values list or required-field rule lives only in
a docstring/comment rather than an enum/schema is a latent false-zero; promote each to a
machine-checkable constraint (the paper's fix is literally one line per case). (2) For the
highest-stakes self-reporting surfaces — the sentinel's alarm classifier, the INBOX
unread-reader, the burn-monitor's rate/level checks — add a second, independent recompute:
e.g. the alarm responder should re-derive "crashed vs. empty" from the subprocess exit code
directly rather than trusting a parsed field; the INBOX reader's zero-count claim should be
cross-checked against a raw grep count on some cadence (which is, not coincidentally,
exactly how this week's false-zero was actually caught — by the Stop hook's independent
INBOX check). (3) Do NOT reach for "have Claude double-check the output" as the verification
layer — 2606.09863 shows that's the weakest option available, worse than a cheap classifier.
**Status: pitched.**

## Pitch 2 — Claude Code now ships harness-level cost-governance hooks: `PreModelSwitch` can block an escalation before it happens, not just log it after

**Technique.** Claude Code shipped two things in the last 10 days that operate one layer
below the fleet's own hand-built cost controls. Verified directly against the vendor
changelog (`code.claude.com/docs/en/changelog`):

- **v2.1.251 (Aug 28, 2026):** "Added `PreModelSwitch` and `PostModelSwitch` hook events
  (block, confirm, or annotate a model switch); `SessionStart` resume hooks now receive
  session staleness and the estimated re-cache cost."
- **v2.1.243 (Aug 25, 2026):** "Added a Loops breakdown to `/usage`: per-loop run count,
  total tokens, tokens per run, and last run, so runaway or chatty `/loop` tasks are easy
  to spot." Same release also added a spend-limit bar to `/usage`, a `rate_limits.spend_limit`
  status-line field, and a `modelPricing` managed setting — note these three are scoped to
  orgs behind a "Claude apps gateway with spend limits," so they may not apply directly to
  a Max-plan setup; `PreModelSwitch`/`PostModelSwitch` and the `/loops` breakdown are not
  gateway-scoped and apply generally.

**Who's doing it.** Anthropic itself, first-party — this is the vendor's own shipped
changelog, about as verified as a software-feature claim gets. Corroborated independently
by the GitHub release tag (`anthropics/claude-code` v2.1.251) and two separate posts from
the `@ClaudeCodeLog` changelog-mirror account quoting the same entries.

**Evidence it's real.** Confirmed by direct fetch of the primary changelog page (exact
version numbers and dates quoted above), not a secondhand paraphrase.

**Need it serves.** Fleet pain #1: cost/burn governance. The fleet just (2026-08-29)
shipped cause-keyed model routing (Kyle-initiated turns → Opus, sweeper/alarm/self-directed
maintenance → Sonnet), a rate-based burn trip alongside the old level-based pause flags, and
a per-summon $ ceiling ($20→$4) — all *application-layer* overlays that infer intent and
police spend *after* tokens are already committed to an API call, and STATUS.md already
recorded one gap in exactly this shape (the pause flag not binding on the reactive
mail-triggered summon path — the two scheduled scripts had the guard, the path that
actually spends money didn't). `PreModelSwitch` is a **harness-level gate**: it can
categorically deny an escalation to Opus before the call happens, closing that class of gap
by construction rather than by more careful bookkeeping. Priority: **(2)** — cheaper,
more reliable self-running maintenance is exactly the multi-agent-without-Kyle unlock, and a
harness-enforced ceiling means fewer alarms needing his attention. Modest spillover to
**(3)**: a bounded-cost trading-sentinel triage path is a resilience property too.

**Whole-fleet leverage.** Converts the fleet's cause-keyed routing policy from "a rule
every summon has to remember to check" into "a hook the harness enforces regardless of
whether the summon remembers" — the same rules-vs-hooks upgrade the fleet has already
applied elsewhere (2026-09-01's `handoff-guard`, 2026-08-27's hooks-audit build-pitch),
now available for the specific policy that's driving 76% of monthly Claude spend.

**Build sketch.** (1) Wire a `PreModelSwitch` hook in the summon layer that reads the same
`cause` classification the routing PR (task `383e094899594a43b0a840b11ef0d3c8`) just built,
and denies (not just logs) any switch to Opus where `cause` resolves to
alarm-response/sweeper/tickler/self-directed rather than Kyle-initiated. (2) Add a
`/loops`-derived check to `burn_monitor.py`'s existing rate-trip logic — a summon whose
tokens-per-run climbs relative to its own history is the same "runaway loop" signal Anthropic
built the breakdown to surface, one layer earlier than dollar-based rate tripping. (3) Confirm
whether the fleet's plan actually sits behind a "Claude apps gateway" before assuming the
spend-limit-bar/`modelPricing` features apply — if not, those three are inert and only the
hook + `/loops` breakdown are actionable now. **Status: pitched.**
