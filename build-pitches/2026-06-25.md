## PITCH: Sprint Contracts + Tool-Armed Adversarial Evaluator for Fleet Dispatch

**Technique:** Before a dispatched worker starts building, a fresh-context evaluator negotiates and locks a structured "sprint contract" — the exact acceptance criteria both agents agree define "done." After the worker completes, the evaluator re-enters with bash/shell tool access and actually runs the tests against those criteria, rather than just reading the diff. The loop repeats until the evaluator passes — Kyle is not the fallback. Two additions to the dispatch briefing template, no new infrastructure.

**Who's doing it:**
- **Anthropic Engineering** — "Harness Design for Long-Running Apps" (https://www.anthropic.com/engineering/harness-design-long-running-apps): describes building a 2D game engine in 6 hours and a full DAW in 4 hours using a Planner → Generator → Adversarial Evaluator (with Playwright MCP tools) loop. The blog is from Anthropic's applied AI team, not a third-party demo.
- **Ash Prabaker + Andrew Wilson (Anthropic Applied AI)** — "Build Agents That Run for Hours" workshop at AI Engineer conference (https://www.youtube.com/watch?v=mR-WAvEPRwE, 73k views, 1h15m): detailed implementation walkthrough including why the evaluator needs tools, how to make subjective quality gradable, and "which parts of your harness to delete when the next model drops."
- **The AI Automators** — "Anthropic Just Dropped the New Blueprint for Long-Running AI Agents" (https://www.youtube.com/watch?v=9d5bzxVsocw, 179k views): independent analysis of the same blog post, confirming the two failure modes (context anxiety + poor self-evaluation) and validating the adversarial evaluator as the key fix.
- **Cole Medin** — "Google Just Dropped a Masterclass on Agentic Engineering" (https://www.youtube.com/watch?v=zbmuiaPuiNM): covers Google's independent convergence on the same pattern — the harness is 90%, the model is 10%. Corroborates that sprint contracts and evaluators are where the industry is landing, not a single lab's quirk.

**Evidence it's real:**
- Primary source is Anthropic's own engineering blog (not a demo, not a tweet) — concrete implementation details including specific failure modes, rubric weighting, and an honest admission that out-of-the-box Claude is a "poor QA agent" that talks itself into approving mediocre work.
- The workshop transcript (73k views) walks through three real experiments with specific timings and costs ($71 first pass, $125 total for the DAW). Not a proof of concept — shipped artifacts.
- Two independent channels (179k views combined) analyzed the same blog and arrived at the same conclusion about the sprint contract + evaluator pattern.
- Google published a parallel 51-page guide arriving at the same architecture independently — harness design convergence across Anthropic and Google is a strong signal it's real, not a lab-specific trick.
- Cross-checked against Kyle's existing patterns: the `/qc-episode` skill already uses adversarial skeptics, confirming the pattern works in this fleet. The gap is (a) no sprint contract upstream, (b) no tool-armed evaluator downstream, (c) no loop — just one review pass.

**Need it serves:**
Fleet pain: dispatched workers currently declare work done without a locked success contract, and the PR reviewer reads code but can't execute it. When the loop fails, it bubbles to Kyle — defeating the "multi-agent collaboration that carries work forward without his attention" unlock (his **priority #2**). The dispatch template has a "success criterion" field, but it's defined by the COS unilaterally — the worker never negotiates or locks it. The evaluator (the `code-review` skill) does a single pass and reports; it doesn't run a loop until pass.

**Whole-fleet leverage:** Wiring sprint contracts + a tool-armed evaluator loop into the `delegate` dispatch template closes the "fallback to Kyle" pattern on any build dispatch — the fleet verifies its own work rather than requiring human judgment at every completion boundary.

**Build sketch** (agent-executable, additive to existing dispatch):

**Step 1 — Sprint contract in the dispatch briefing** (~30 min):
In the task-specific addendum of the dispatch briefing (Step 2a of the `delegate` skill), add a mandatory "Sprint Contract" block:
```
## Sprint Contract
Before starting any work, generate a sprint-contract.json:
  { "criteria": [ "<specific verifiable acceptance criterion 1>", ... ], "locked": true }
Write it to the project root. This contract cannot be modified after work begins.
The evaluator will verify each criterion after you complete the task.
```

**Step 2 — Tool-armed evaluator sub-agent** (~60 min):
Add an evaluator step to the dispatch worker's Findings & Decisions footer. After the worker signals completion:
- Spawn a fresh-context sub-agent (via `claude -p` or a workflow `agent()` call) with the sprint-contract.json and bash tool access.
- Evaluator prompt: "Verify each criterion in sprint-contract.json. For each, run the actual test or check that would confirm it (don't infer from code — execute). Return a structured pass/fail with specific failures."
- On fail: return feedback to the worker with specific failures. Worker revises. Repeat.
- On pass: worker files the PR.

**Step 3 — Concrete files to modify**:
- `~/.claude/skills/delegate/SKILL.md` — add Sprint Contract section to the task-specific addendum template.
- `~/.observer/wiki/agent-os/evaluator-agent-prompt.md` (new file) — reusable evaluator agent prompt, parameterized by sprint-contract.json path.
- Any active `*.sh` dispatch scripts in `~/observer-system/` that hard-code the PR-filing step — wire the evaluator before the `gh pr create` call.

**Harness evolution note (secondary, no build required):** Anthropic explicitly calls out that harness components encoding model limitations go stale as models improve. Context resets were a Sonnet 4.5 workaround; Opus 4.6 eliminated the need. Implication for the fleet: after each major model upgrade, audit the dispatch template for workarounds that are no longer necessary and prune them. The Fleet Optimizer's next weekly survey should ask: "which harness constraints were added for a specific model, and has that model been superseded?"
