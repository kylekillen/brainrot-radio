## PITCH: Independent Outcome Grader — Add a `gradeAndRevise()` Helper to Fleet Workflows

**Technique.** When an agent evaluates its own output, it carries the full context of how it produced that output — which means it can rationalize past failures and miss errors it already framed as acceptable. The Independent Outcome Grader pattern fixes this by splitting generation and verification into two completely separate context windows. A writer agent produces the artifact; a grader agent, spawned fresh with no access to the writer's reasoning chain, reads only the final output against a rubric and either passes it or returns a per-criterion list of gaps. If the grader rejects, the writer revises — and the loop repeats up to a cap. This is not self-evaluation; the grader has no idea how the writer arrived at its output, so it cannot inherit the writer's blind spots.

**Who's doing it.**

The `user.define_outcome` API provisions a rubric-driven grader that runs in its own hosted sandbox after each writer turn.
- **Anthropic Cookbook** — full worked example with code at https://platform.claude.com/cookbook/managed-agents-cma-verify-with-outcome-grader. The rubric design principle is explicit: "make the grader earn approval" — a vague criterion like "cover demand charges" lets the grader skim; a specific one like "state a $/kW figure" requires actual verification.

**Need it serves.**
The fleet's biggest trust problem with dispatched workers is that they self-evaluate. When a beat reporter writes a segment and the `/qc-episode` skeptics review it, those skeptics read the same script the writer produced — they know which sources were cited, which claims were made, what the narrative arc is. They cannot independently verify that a cited URL actually says what the writer claims, or that a quoted figure is accurate. This is the same failure mode CMA's grader was built to fix.

Specific fleet pain points this addresses:
- **Beat reporters** (this podcast): reporters cite sources but no step independently fetches and checks those sources. A grader with rubric "fetch each cited URL and confirm it supports the stated claim" catches hallucinated or misrepresented citations.
- **Alarm investigators** (observer-system): when a worker concludes "this is a benign sizing alarm, no action needed," that conclusion is based on the same data the worker interpreted. A grader with rubric "fetch the raw position log entry and confirm the sizing number matches the claim before approving" is a harder gate.
- **Dispatch workers generally**: any workflow where a worker produces a deliverable and Kyle is supposed to trust it. An independent grade-and-revise pass before the task is marked done reduces the rate of "looks good but was wrong" completions.

**Priority served:** Priority #2 (multi-agent collaboration that carries work forward without Kyle's constant attention). The gradeAndRevise pattern makes "done" mean something — an output has been independently verified, not just self-assessed. Kyle can trust the deliverable without reviewing it himself.

**Whole-fleet leverage.**
One reusable `gradeAndRevise(taskPrompt, rubric, maxIterations)` helper, added to fleet Workflow templates, upgrades every dispatched worker's output quality without requiring model changes or new infra. The Fleet Optimizer already rated this as the next enhancement to the fleet's workflow dispatch layer.

**Build sketch** (an agent could implement this cold from this file):

1. **Create `~/.claude/workflows/helpers/grade-and-revise.js`** — a pure function:
   ```javascript
   async function gradeAndRevise(taskPrompt, rubric, maxIter = 3) {
     let draft = null
     for (let i = 0; i < maxIter; i++) {
       draft = await agent(
         draft ? `Revise based on this feedback:\n${draft.feedback}\n\nOriginal task: ${taskPrompt}` : taskPrompt,
         { label: `writer:iter${i}` }
       )
       const verdict = await agent(
         `You are a grader. You have not seen how this was written — only the output below and this rubric.
         
         RUBRIC:
         ${rubric}
         
         OUTPUT TO GRADE:
         ${draft}
         
         Return JSON: { "passed": true/false, "feedback": "...", "per_criterion": {...} }`,
         { label: `grader:iter${i}`, schema: VERDICT_SCHEMA }
       )
       if (verdict.passed) return { result: draft, iterations: i + 1, verdict }
       draft = { content: draft, feedback: verdict.feedback }
     }
     return { result: draft.content, iterations: maxIter, verdict: { passed: false } }
   }
   ```

2. **Pilot: beat reporters.** Update the beat reporter dispatch in `generate-episode.sh` to wrap each beat's write step in `gradeAndRevise()` with a rubric requiring: "For each factual claim with a source URL, fetch that URL and confirm the cited page contains the stated information. Return FAIL if any citation cannot be independently verified."

3. **Pilot: alarm investigator.** Update `responder.sh`'s judgment-tail path: after the worker produces an investigation conclusion, pass it to a grader with rubric "Fetch the raw sentinel event log at [path]. Confirm the position size, direction, and ticker in the conclusion match what's in the log before approving." Zero trust on the writer's interpretation.

4. **Key rubric design rule:** Grader criteria must force the grader to DO WORK, not just read the writer's prose and agree with it. Specific, verifiable, action-requiring criteria (fetch, count, match) beat general quality criteria (well-written, complete, accurate).
