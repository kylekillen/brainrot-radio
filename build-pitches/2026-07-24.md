## Pitch 1 — Coordinator/executor model tiering within Claude dispatch (Opus/Fable-5 plans, Sonnet executes)

**Technique:** Split every multi-step Claude dispatch into a strong-model coordinator (plans, reviews, judges) and a cheap-model executor (writes the actual code/content), instead of running every step on the frontier tier. Cached context on repeat calls to the same persistent sub-agent session costs ~10% of fresh input tokens, which is why this beats a single "advisor" call.

**Who's doing it:** AI Jason, ["Tmux + Fable = Cut 35% less token"](https://www.youtube.com/watch?v=wCSPgHpcxdc) (2026-07-20) — describes this as Claude Code's own official recommendation, and cites Devin's "Fusion" harness (Opus-tier orchestrator + Sonnet-tier worker) beating a plain advisor-pattern at 35% lower cost for equivalent output. Matthew Berman, ["You NEED to do this (HUGE AI SAVINGS)"](https://www.youtube.com/watch?v=QNEo_tl-nhw) (2026-07-23) — walks concrete per-stage token math for a real task: Fable-5-only costs $81, a plan/execute/review mix (Fable plans → cheap model executes → frontier model reviews) costs $25.55 for the same result, a ~68% cut.

**Evidence it's real:** Cross-checked beyond the two videos — Data Science Dojo has a dedicated post titled "[Fable 5 as Orchestrator, Sonnet as Executor: A Guide to Cut Claude Code Costs](https://datasciencedojo.com/blog/claude-code-fable-5-orchestrator-workflow/)"; CloudZero's Claude Code cost analysis independently measures a 1-Opus + 4-Sonnet team at ~40% cheaper than 5 Opus agents ($48.75/day vs $81.25/day at June-2026 rates); MindStudio has two separate posts on the same pattern; there's already a maintained open-source tool ([pilotfish](https://github.com/Nanako0129/pilotfish)) built specifically to automate this multi-model orchestration for Claude Code. Four independent sources, concrete published numbers, a real tool built around it — not a single demo.

**Need it serves:** Need #1, credit resilience (`credit-resilience-plan.md`) — directly reduces the burn that has repeatedly blacked out the alarm-responder and forced the podcast pipeline off. Serves priority #2 (AI-business multi-agent unlock: cheaper per-dispatch cost means more delegated work fits inside the weekly credit budget without a burn crisis pulling Kyle's attention, which is priority #1's protection).

**Whole-fleet leverage:** The FO's own 2026-07-20 scan already confirmed this exact gap is unbuilt in our tooling defaults — the Workflow tool's `agent()` guidance says "default to omitting" model overrides, and `observer_heartbeat.sh` runs all 7 compile steps uniformly on sonnet/medium with no complexity-based tiering. This pitch doesn't re-discover the gap; it adds two more independent corroborating sources, concrete before/after cost math to benchmark against, and a copy-pasteable implementation template (AI Jason's CLAUDE.md delegation-rule section, published in his AI Builder Club GitHub repo) — the piece the earlier scan didn't have.

**Build sketch:**
1. Audit dispatch call sites that currently omit a model — start with `observer_heartbeat.sh`'s 7 compile steps and the Workflow tool defaults the FO already named.
2. Classify each dispatched subagent call: planning/architecture/judgment → keep on the strongest tier; mechanical execution/formatting/rote coding → route to Sonnet (or a cheaper external model per the existing `external-model-routing.md` table).
3. Add an explicit coordinator/executor delegation-rule block to the relevant CLAUDE.md files (COS, fleet-optimizer, dispatcher): coordinator does design/plan/review, delegates hands-on execution to Sonnet-tier subagents, and sub-agents must not spawn nested sub-agents.
4. Measure token spend on one representative workload (e.g., one day's compile-step run) before/after tiering, and verify output quality didn't regress — the FO's own note flagged "needs a quality-preservation check first," so that check is part of the build, not optional.
5. Land it as a change to dispatch tooling defaults, not a prompted habit.

**Status: pitched.**

## Pitch 2 — Docker Sandboxes for unsupervised/skip-permissions agent dispatch

**Technique:** Run any agent operating in "YOLO mode" (skip-permissions / fully autonomous) inside a Docker Sandbox — a per-agent microVM with its own filesystem mount, process space, Docker engine, and network allowlist — instead of giving it raw access to the host filesystem.

**Who's doing it:** Cole Medin, ["How to Actually Run Your Coding Agent Safely (And Avoid the Horror Stories)"](https://www.youtube.com/watch?v=zb2LyMro77M) (2026-07-23) — live-demos `sbx run claude`, then verifies isolation on camera: a sandboxed session can't read `~/.ssh`, can't reach a host-machine service, can't touch the host Docker socket, and network requests off an allowlist get blocked before they leave the box.

**Evidence it's real:** Not just one YouTuber — Docker's own official blog post, "[Docker Sandboxes: Run Claude Code and Other Coding Agents Unsupervised but Safely](https://www.docker.com/blog/docker-sandboxes-run-claude-code-and-other-coding-agents-unsupervised-but-safely/)," confirms this is a real, actively developed Docker product (microVM isolation, macOS/Windows support since 2026-01-30, explicit Claude Code/Codex/Gemini CLI/Kiro support). Independent third-party write-ups (MintMCP's "How to Sandbox Claude Code," CodeOnGrass's Docker-sandbox walkthrough, a maintained GitHub gist tracking the broader "coding agent sandboxes" category) corroborate it's a known, adopted practice, not a one-off trick.

**Need it serves:** This is not a hunt for a novel problem — it's a fix for a failure class our OWN fleet has already hit and logged repeatedly this month: "⚠️ `~/observer-system` IS the deploy: I edited the canonical checkout and the live fleet ran my uncommitted work-in-progress" (2026-07-17), "The canonical-tree edit slips between READ and WRITE, not at intent" (2026-07-17), COS's canonical-worktree checkout guard firing mid-session (2026-07-17), and a test suite that silently wrote fixture rows into live fleet state under `#272`. The current defense is a git-worktree *convention* — discipline, not a mechanism — and it has already produced at least one live-state corruption plus several near-misses. Serves priority #2 directly: Kyle's stated unlock is delegated work that "carries forward without his constant attention," which only scales safely if an unsupervised worker structurally *cannot* damage shared state or credentials, rather than depending on every worker remembering `git worktree add`.

**Whole-fleet leverage:** Swaps a discipline-dependent convention for OS-level isolation that can't be forgotten — a structural fix for the single most-repeated bug class in the fleet's own ledger this month, not a habit fix.

**Build sketch:**
1. Install Docker Sandboxes (single command, free, works alongside existing Docker Desktop use).
2. Pilot on the highest-incident-history path first: replace "always `git worktree add`" with "always `sbx run claude --clone`" (full-clone isolation) for headless/unsupervised worker dispatch (the delegate skill, PR-review-sweeper workers, any worktree-isolated `Agent`/`Workflow` call).
3. Configure a network allowlist using the same reasoning already in `external-model-routing.md`'s provider allowlist.
4. Verify isolation the way the video does, on our own machine, before trusting it: confirm a sandboxed worker can't see `~/.ssh`, can't reach the host Docker socket, can't touch files outside its mounted workspace.
5. Only after the pilot is proven, consider extending sandboxed dispatch near trading-bot directories (`mojo-daemon/copybot`, `arena-bot`) — get Kyle's explicit sign-off first, since those paths are money-adjacent even though the sandboxing mechanism itself isn't a trading-practice change.

**Status: pitched.**
