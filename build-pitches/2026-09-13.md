## The find: the Agent SDK's official session-management surface covers more of the stalled spec's gap than the spec knew about — and one fact in it is a direct blocker-check for the fleet's own CLI version
**Technique.** Anthropic's Claude Agent SDK (the library underneath Claude
Code, separate from but compatible with the CLI binary the fleet shells)
documents a full session-management surface beyond the bare `--resume` flag:
`resume`/`continue`/`fork_session` options on `query()`; `session_id` on
every result message; and, more than the fleet's spec surfaced, a
**`SessionStore` adapter interface** (`append`/`load`, plus optional
`listSessions`/`delete`/`listSubkeys`) with **shipped reference
implementations for S3, Redis, and Postgres** in the SDK's own GitHub repo,
purpose-built so "a session created on one host can be resumed on another
host." Alongside it: `tag_session`/`rename_session`/`get_session_info`/
`list_sessions` for structured session bookkeeping instead of a bespoke
sidecar file.

**Two concrete facts that change what's buildable right now:**
1. **Cross-directory resume already works on this fleet's installed CLI.**
   The docs state cross-project session lookup (searching beyond the current
   working directory to find a session ID) was added in CLI **v2.1.223**;
   before that, lookup was scoped to the same project directory. I checked —
   `~/.local/bin/claude --version` on this machine reports **2.1.269**. The
   fleet is already past the version gate; nothing needs upgrading to get
   this behavior on the raw `--resume` flag the spec already identified.
2. **`SessionStore`/`tag_session`/etc. are Agent SDK functions, not CLI
   flags** — and `summon.py` shells the CLI binary directly, so getting them
   requires swapping the runner to the `claude_agent_sdk` Python package (a
   real migration, not a config change). The **lower-lift alternative the
   docs also document**: for cross-host resume without an SDK migration,
   just copy the session's `.jsonl` file from
   `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl` onto the target host
   under any directory below `~/.claude/projects/` before calling `--resume`
   — a plain file copy, no SDK dependency.

**Who's doing it / corroboration.** No qualifying claude_lab video existed
this week (see above), so this pitch is sourced and cross-checked entirely
against documentation and independent technical write-ups instead of a
demo — arguably stronger verification, not weaker: primary source
[code.claude.com/docs/en/agent-sdk/sessions](https://code.claude.com/docs/en/agent-sdk/sessions)
and [code.claude.com/docs/en/agent-sdk/session-storage](https://code.claude.com/docs/en/agent-sdk/session-storage)

[developersdigest.tech's "Resume Subagents" guide](https://www.developersdigest.tech/guides/resume-subagents)
(names the exact restored state: "the subagent's context, recent tool output,
and in-flight task list," plus the caveat that "resume is per-subagent —
resuming one worker doesn't resume the whole team"), and
[claudefa.st's persistent-subagents write-up](https://claudefa.st/blog/guide/agents/persistent-subagents).
Cross-checked that this isn't already on the fleet's radar: grepped

v2.1.223 cross-directory fix, and the file-copy fallback were not.

**Evidence it's real, not hype.** Official docs ship a runnable conformance
suite (`run_session_store_conformance` in Python, `conformance.ts` in
TypeScript) that any adapter must pass — a testable contract, not a slide.
The docs are also candid about limits: `forkSession` is "not a byte copy" (it
rewrites session IDs and remaps message UUIDs on every fork — copy-shortcuts
produce broken transcripts), store mirroring is "best-effort" with documented
retry/dedup requirements, and resuming a subagent restores only that
subagent, not the whole team. Specific, falsifiable claims — not a pitch
deck.

## Build sketch
1. **Phase 0 spike, now unblocked to start:** in `summon.py`, capture
   `session_id` from the CLI's stream-json output on every summon (the spec
   already found this field is present live), and add a field to each role's
   `roles.json` entry recording the most recent session id per role.
2. **Phase 1:** on the next wake for a role with a stored session id, pass
   `--resume <id>` instead of building the cold seed from
   HANDOFF/STATUS/INBOX. Fall back to cold-start if `--resume` fails (e.g.
   the transcript aged out under `cleanupPeriodDays` retention).
3. **Cross-host case (mini migration):** don't reach for `SessionStore`/SDK
   migration yet — first try the documented lower-lift path: locate
   `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl` on the source host,
   copy it under a matching path on the target host, then `--resume` there.
   Cheap to test, reversible, no new dependency.
4. **Defer the SDK migration** (swapping `summon.py`'s raw
   `subprocess.Popen([CLAUDE_BIN, ...])` for the `claude_agent_sdk` Python
   package to get `SessionStore`/`tag_session`/`list_sessions`) to a later
   phase — real value (structured cross-host bookkeeping, S3/Redis/Postgres
   reference adapters ready to copy), but a bigger lift than the spec's
   stalled ask, and not needed to unblock Phase 0/1.
5. Route this whole thread back into the existing spec doc
   (`2026-09-06-checkpoint-resume-claude-role-sessions-spec.md`) rather than
   starting a parallel one — it already has the role-by-role
   `cold_resume_proven` groundwork; this pitch adds facts, not a competing
   design.
