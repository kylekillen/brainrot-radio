## PITCH #1 (primary): Per-Skill Validation Hooks — Deterministic Self-Checks Embedded in Every Worker

**Technique.** Claude Code now supports hooks declared directly in skill and subagent frontmatter — not just global `settings.json`. A `Stop` or `PostToolUse` hook embedded in a skill's YAML fires automatically each time that specific command runs, executing a deterministic shell script that validates the output before the agent reports success. The effect: every dispatched worker gains an unfakeable pass/fail check that's scoped to exactly the thing that command is supposed to produce. No new infrastructure. No LLM self-assessment. The pattern is "agents + deterministic code beats agents alone" — the model can't rationalize away a failing shell exit code.

**Who's doing it.** IndyDevDan published "The Claude Code Feature Senior Engineers KEEP MISSING" (https://www.youtube.com/watch?v=u5GkG71PkR0), calling this a release "most engineers have missed" and "buried in the release notes." He demos: a CSV-editing skill with a `PostToolUse` hook that runs a pandas validator after every file write — when the output is broken, the hook fires exit code 2, the agent auto-fixes, and *then* reports done. He extends the same pattern to HTML validation, code linting, and a full multi-step finance pipeline where every agent in the chain self-validates. Anthropic officially documented it in their June 18, 2026 blog post ("Steering Claude Code: skills, hooks, subagents and more," https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more): "Hooks are registered in settings.json, managed policy settings, or skill/agent frontmatter."

**Evidence it's real.** Anthropic's June 18 blog post is the authoritative source. Multiple independent community guides confirm the same. IndyDevDan shows a working demo with validator log output. Grep of Kyle's entire `/skills/` tree confirms **zero existing skills use per-skill hook frontmatter** — only global `settings.json` hooks exist. The gap is real and the feature is live.

**Need it serves.** The `loop-methodology-adoption` doc (June 21) flags this directly: "Verification is mostly LLM-as-judge in-context… the podcast QC and the `/goal` judge are LLM-as-judge." The Fleet Optimizer STATUS (June 22) showed a stale runner prompt that instructed agents to do already-completed work for weeks — a failure mode scoped `Stop` hooks would catch. Serves **Priority 2** (multi-agent work advancing without Kyle's attention) because workers that verify their own outputs need zero babysitting.

**Whole-fleet leverage.** Every dispatched worker gains a deterministic pass/fail gate — silent failures (agent looks done, actually isn't) are eliminated fleet-wide with no new infrastructure.

**Build sketch** (agent-pickable, no Kyle involvement needed):
1. Create `.claude/skills/validators/` with three shell validators:
   - `check-qc-pass.sh` — `grep -q "QC VERDICT: PASS" "$1" || { echo "QC VERDICT not found"; exit 2; }`
   - `check-mp3-exists.sh` — `ls "$1"/killen-time-*.mp3 1>/dev/null 2>&1 || { echo "No MP3 in $1"; exit 2; }`
   - `check-wordcount.sh` — fail if word count < 14000 (the CLAUDE.md floor)
2. Add `Stop` hook to `/qc-episode.md` frontmatter pointing at `check-qc-pass.sh`
3. Add `Stop` hook to `/publish-episode.md` pointing at `check-mp3-exists.sh`
4. Add `Stop` hook to `/assemble-episode.md` pointing at `check-wordcount.sh`
5. (Stretch) Add `Stop` hook to `/delegate` skill → validate spawned worker registered with Remote Control

Each validator is ≤30 lines of shell, co-located in `.claude/skills/validators/`. Total build: ~2 hours. Rollback: remove frontmatter lines.

**Status: pitched**

## PITCH #2: Dreaming Without CMA — Scheduled Memory Curation for Every Fleet Role

**Technique.** Anthropic's "Dreaming" feature (launched May 6, 2026 in Claude Managed Agents) runs a background process *between* agent sessions that reviews accumulated memory and context: pruning stale or completed instructions, merging duplicates, and surfacing patterns that no single session could identify across the full history. The result is that each session starts with a cleaner, more accurate context than the previous one left behind — without fine-tuning, weight updates, or any model change. It's pure context curation. Dreaming requires CMA to run automatically, but the same pattern is implementable on the fleet today using a scheduled Haiku job that reads each role's memory and handoff files, proposes curated replacements, and writes them to a staging area for the Fleet Optimizer to promote on review.

**Who's doing it.**
- **Anthropic (official)** — shipped Dreaming as part of Claude Managed Agents public beta at Code with Claude, May 6, 2026: https://claude.com/blog/new-in-claude-managed-agents
- **VentureBeat** — "Anthropic introduces 'dreaming,' a system that lets AI agents learn from their own mistakes" (May 6, 2026): https://venturebeat.com/technology/anthropic-introduces-dreaming-a-system-that-lets-ai-agents-learn-from-their-own-mistakes
- **Harvey (legal AI)** — reported 6× task completion rate increase after Dreaming; improvement driven by agents requiring fewer clarification rounds and fewer error corrections per task. Source: https://www.abhs.in/blog/anthropic-dreaming-claude-managed-agents-self-improve-harvey-wisedocs-2026
- **Wisedocs (medical document review)** — cut document review time 50% using Dreaming + Outcomes. Source: https://letsdatascience.com/blog/anthropic-dreaming-claude-managed-agents-self-improving-may-6
- **Fleet Optimizer STATUS.md (June 22, 2026)** — independently identified this pattern as "Survivor 2 (medium-high)" from an external scan, with live fleet evidence: the Fleet Optimizer's own runner prompt was stale — it kept instructing every run to "rebuild the already-done alarm-triage feature" (PR #125, deployed and working since June 18). That's the exact class of bug Dreaming prevents. The note: "implementable without CMA: weekly Haiku call over HANDOFF.md + memory files → staged curated replacement → Fleet Optimizer promotes on review."
- **Supporting overview:** https://www.innobu.com/en/articles/claude-managed-agents-dreaming-outcomes-orchestration.html

**Evidence it's real.**
Four independent signal layers: (1) official Anthropic release with documentation; (2) two production case studies with quantitative results (Harvey 6×, Wisedocs 50%); (3) VentureBeat and six other tech publications covering the launch; (4) the Fleet Optimizer's independent identification on June 22 from observed fleet behavior — it reached the same conclusion without knowing about any of the above coverage. The convergence is the verification. The live stale-prompt incident is the proof-of-need: an already-completed feature kept being re-assigned to agents because the runner prompt was never updated. That's context drift; Dreaming is the fix.

Note on availability: Dreaming's automated version is a Claude Managed Agents feature (research preview). This pitch is specifically about the "Dreaming Without CMA" translation — implementing the same memory curation pattern as a scheduled process using the fleet's own tools, without needing to migrate to CMA.

**Need it serves.**
Fleet pain: Context drift. Every long-running role in the fleet accumulates stale instructions — completed work that wasn't pruned, superseded configs that weren't removed, handoff notes that became irrelevant three PRs ago. The Fleet Optimizer's stale runner prompt is Exhibit A (live, recent, self-documented in STATUS.md). The COS, the alarm responder, and the brainrot-radio pipeline CLAUDE.md all accumulate similar drift over time. No automated process currently reviews and prunes this context.

Serves Kyle's **priority #2** (multi-agent collaboration that carries work forward without Kyle's constant attention): agents running on stale instructions produce redundant work or make wrong decisions. Curated, accurate context is the substrate that enables truly autonomous operation. A weekly curation pass means each new worker dispatched is briefed against clean, current state rather than accumulated cruft.

**Whole-fleet leverage:** One scheduled weekly Haiku curation job, reading each role's accumulated memory and handoff files and proposing pruned replacements, prevents the "stale instruction → wasted or wrong worker run" failure mode across all fleet roles simultaneously. Marginal cost is one cheap Haiku call per role per week — trivially low. Applies immediately to: Fleet Optimizer runner prompt, COS HANDOFF.md, brainrot-radio CLAUDE.md notes, observer-system calibration files, alarm responder context.

**Build sketch** (an agent could implement this cold from this file):

1. **Create `~/fleet-optimizer/dreaming.sh`** — the curation script:
   ```bash
   #!/bin/bash
   # Reads each role's memory + handoff files, proposes curated replacements
   ROLES=(
     "fleet-optimizer:~/fleet-optimizer/HANDOFF.md"
     "cos:~/.observer/wiki/calibration.md"
     "brainrot-radio:~/brainrot-radio/CLAUDE.md"
   )
   for role_entry in "${ROLES[@]}"; do
     role="${role_entry%%:*}"
     file="${role_entry##*:}"
     mkdir -p ~/.dreaming/staged/$role/
     claude -p --model claude-haiku-4-5-20251001 "You are reviewing the accumulated context file for the '$role' fleet role.
     
   TASK: Curate this file. For each item, mark it as one of:
   - REMOVE: completed work that is no longer a standing instruction (check git history if needed)
   - MERGE: duplicate of another item — combine and remove the duplicate  
   - RETAIN: still current and actively needed
   - ADD: cross-session pattern you detected that should be documented
   
   Output a curated replacement file with the same format. Do NOT change the structure or headers — only remove stale content and add missing patterns.
   
   FILE: $(cat $(eval echo $file))" > ~/.dreaming/staged/$role/$(basename $file)
   done
   echo "Dreaming complete. Review staged replacements in ~/.dreaming/staged/ before promoting."
   ```

2. **Register in launchd** — add a `com.mojo.fleet-dreaming.plist` that runs `dreaming.sh` weekly (e.g., Sunday 3am when other jobs aren't active). Log output to `~/.dreaming/dreaming.log`.

3. **Fleet Optimizer review step** — add a check at the start of each Fleet Optimizer run: `if staged files exist in ~/.dreaming/staged/, diff them against the live files and present a summary. If clean, promote (mv staged/* to live). If changes look wrong, log a warning and skip.` This keeps a human-in-the-loop on the promotion without requiring Kyle to intervene manually on every run.

4. **Pilot on Fleet Optimizer itself first** — its runner prompt's stale-rebuild incident is documented, making it the easiest case to verify the pattern works (the diff should clearly show the "rebuild alarm-triage" instruction getting removed).

5. **Extend to CLAUDE.md files** — the brainrot-radio CLAUDE.md and observer-system CLAUDE.md accumulate the same class of drift. After the Fleet Optimizer pilot succeeds, extend the role list.

**Status: pitched**
