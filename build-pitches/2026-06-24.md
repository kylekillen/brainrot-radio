## PITCH: `fallbackModel` Chain — Fleet-Wide Overload Resilience in Two Lines of JSON

**Technique.** Claude Code v2.1.166 shipped `fallbackModel`, a native config setting that chains up to three fallback models tried in order whenever the primary model returns a 529 overload error or is unavailable (retired, unreachable). Configure it once in `~/.claude/settings.json` and every fleet `claude -p` call — launchd jobs, background agents, dispatched workers — gains an automatic safety net with zero per-script changes. The switch is bounded to the turn that hit overload; the next turn retries the primary model first. An unavailable model in the chain is silently skipped.

**Who's doing it.**
- **Anthropic (primary source)** — shipped in v2.1.166–v2.1.169, Week 24 (June 6–8, 2026). Official docs: https://code.claude.com/docs/en/model-config#fallback-model-chains. Week 24 release note: "fallbackModel configures up to three fallback models tried in order."
- **YouTube: "Finally! Claude Code Gets Fallback Models & Security Hardening"** — https://www.youtube.com/watch?v=Um9lVyroxoI. Transcript: "The moment your primary model flags, Claude Code works a chain of up to three fallbacks in order automatically. Stack thinking controls on top. And latency and token burn drop the second the fallback takes over. One retry on unexpected API errors covers the rest. That is how you protect a 10-hour overnight pipeline."
- **Corroborating articles:** digitalapplied.com ("Claude Code Adds Safe Mode and Fallback Model Chains"), aiforanything.io ("Claude Code fallbackModel: Fix 529 Overload Errors and Build Resilient Agent Sessions"), edgee.ai ("Fallback Models — Claude Code that never stops"), avinashsangle.com ("Claude Code Fable 5: Model Routing, Fallbacks, Cost Control").

**Evidence it's real.** Feature confirmed in official Claude Code release notes and documentation. Kyle's current version is v2.1.183 — the feature has been live for 16 days. Multiple independent practitioners have written implementation guides. NOT in Kyle's fleet yet: the Fleet Optimizer's June 22 work pinned explicit `--model claude-opus-4-8` flags on critical paths, but did not add a fallback chain. Grep of `~/.observer/`, `~/brainrot-radio/generate-episode.sh`, `~/fleet-optimizer/run-fleet-optimizer.sh`, and `~/.observer/alarms/responder.sh` confirms zero `fallbackModel` entries.

**Need it serves.**

Fleet pain: The Fleet Optimizer pinned explicit model flags on high-priority paths (June 22). Those pinned calls now have zero overload fallback — a 529 from Opus 4.8 fails the turn completely and surfaced as the caller's error. Two known failure classes affect the fleet: (1) monthly-spend-limit exhaustion, which causes rc=1 with "You've hit your monthly spend limit" — this is the credit SPOF addressed by the Gemini offload plan; and (2) overload 529s and model unavailability — distinct failure mode, unaddressed until now. `fallbackModel` solves class 2; it does NOT solve class 1.

Directly serves **Priority 3** (trading system resilience): the alarm responder at `~/.observer/alarms/responder.sh` spawns a `claude -p` worker on every alarm. A 529 overload currently fails the alarm entirely and leaves it in `active/` un-triaged. With a fallback chain, an overloaded Opus turn auto-retries on Sonnet — the alarm still gets processed. This is additive to the existing triage credit-saver (PR #125, which handles spend-limit exhaustion through rule-decidable code triage); together the two cover both failure classes.

Serves **Priority 2** (multi-agent work forward without Kyle's attention): background agents, the brainrot-radio launchd job, and any future dispatched workers gain automatic overload recovery with no code changes.

Also covers the **Fable 5 metering edge case**: Fable 5 has a built-in content-based fallback to Opus, but `fallbackModel` adds overload protection ON TOP of that — so a Fable 5 session that's both safety-flagged AND the Opus fallback is overloaded has a third-tier Sonnet path.

**Whole-fleet leverage.** One `~/.claude/settings.json` edit applies automatically to every `claude -p` call in every fleet launchd job, every background agent, every dispatched worker — no per-script edits, no new infra, trivially reversible (remove the key). The most model-critical paths (alarm responder, Fleet Optimizer runner) now have explicit pins + an automatic fallback chain underneath.

**Build sketch** (agent-pickable, no Kyle involvement needed):

1. **Add to `~/.claude/settings.json`:**
   ```json
   {
     "fallbackModel": ["claude-sonnet-4-6", "claude-haiku-4-5"]
   }
   ```
   This applies to all fleet calls. Chains are capped at 3 after duplicate removal; extra entries ignored. Aliases work: `["sonnet", "haiku"]` also valid.

2. **Belt-and-suspenders for the alarm responder** — add `--fallback-model claude-sonnet-4-6` to the explicit `claude -p` call in `~/.observer/alarms/responder.sh`. The `--fallback-model` CLI flag takes precedence over settings.json per the docs, so this doesn't conflict with the user-level setting; it just makes the alarm responder's chain explicit and auditable. (One flag at line ~146 of responder.sh where the worker is spawned.)

3. **Document in ACTION-LOG.md** (Fleet Optimizer pattern): note the two-line change, the triggering condition (overload 529s, not spend-limit), and the rollback (remove `fallbackModel` key from settings.json, remove `--fallback-model` flag from responder.sh).

4. **Verify:** run `claude -p "echo 1"` — no change to normal behavior. Feature is already live on v2.1.183; it only activates on overload.

Total build: 10 minutes. Rollback: remove two lines.

**What this does NOT fix:** monthly-spend-limit exhaustion (rc=1 "You've hit your monthly spend limit"). That's a billing error, not an overload, and `fallbackModel` docs explicitly state it does NOT trigger on "authentication, billing, rate-limit, request-size, and transport errors." The credit-resilience-plan's Gemini Flash offload (move #2a) and the dedicated PAYG key (move #3) remain the right solutions for that class of failure.

**Status: pitched**
