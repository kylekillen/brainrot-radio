## Pitch 1 — Test impact analysis + parallel pytest for the single-runner CI

**Technique.** Stop running the full ~6,265-test pytest suite on every CI run. Add a deterministic *selector* (run only tests affected by the diff, from recorded history/dependency data) on the PR lane with a full run kept as backstop on main, and turn on `pytest-xdist` (`-n auto`) so even a full run uses the machine's 12 cores.

**Who's doing it.**
- Anthropic, "Agentic coding is straining CI. Here's how we scaled test impact analysis at Anthropic" (Sep 14, 2026): https://claude.com/blog/agentic-coding-is-straining-ci-heres-how-we-scaled-test-impact-analysis-at-anthropic — CI jobs grew 25x in six months as Claude wrote ~80% of code; a listener + selector service decides which tests run per change; three stop-gap patches lasted 70 days, 29 days, <1 day before a stateless redesign. Their explicit advice: assume 25x load within two quarters.
- Meta, "Predictive Test Selection" (ICSE 2019): https://arxiv.org/abs/1810.05286 and https://engineering.fb.com/2018/11/21/developer-tools/predictive-test-selection/ — ~half the testing infrastructure cost, >95% of individual test failures and >99.9% of faulty changes still caught.
- Open-source implementation for Python: `pytest-testmon` (https://github.com/tarpas/pytest-testmon; Instawork writeup reports ~2x faster CI: https://engineering.instawork.com/test-impact-analysis-the-secret-to-faster-pytest-runs-e44021306603) and `pytest-xdist` (https://pytest-xdist.readthedocs.io/); docs say the two are used together.

**Evidence it's real.** Three independent sources on the technique (Anthropic, Meta paper, a third-party engineering team) agree on the shape, including the same caveat: selection is only as good as its data freshness, and you keep a full-run backstop. The *need* is measured in our own repo, not borrowed (checked 2026-09-19 with `gh run list/view` in `~/observer-system`):
- `uv run pytest -q` = **775 s of a ~800 s CI run**; lint + type-check + install total ~20 s. Pytest is the entire cost.
- CI runs on **one** self-hosted runner (`macos-fleet`, per `ci.yml` comments), so runs serialize. Last 300 runs: 204 PR + 96 push; **84 cancelled (28%)**, 41 failed. Busiest recent day, 09-14: 88 runs. (Wall-clock per run from createdAt→updatedAt includes queue wait, so treat "1,616 runner-min that day" as an upper bound — but 88 runs × ~13 min cannot fit in 24 h serially, which is itself the signal that runs queue and get cancelled.)
- No existing test-selection or parallelism: grep of `pyproject.toml`, `ci.yml` and fleet STATUS/wiki finds no xdist/testmon/selection work. The only CI-cost work so far was `paths-ignore` for STATUS.md-style pushes and the move to a self-hosted runner (for billing, not speed).
- The pain shows up in fleet logs: PRs waiting on `checks_pending` in the sweeper, CI-red triage tasks, and the June-25 "day-long block" cited in the babysit skill.

**Need it serves.** Multi-agent throughput: every fleet-authored PR (reviewer → sweeper → merge) waits on one 13-minute serialized queue. Moves **priority 2** (multi-agent work landing without Kyle) and, indirectly, the machine's CPU headroom for the rest of the fleet (the runner shares the Mac).

**Whole-fleet leverage.** Cuts the PR merge-latency floor that every code-writing role in the fleet sits behind, and frees runner/CPU time; roughly a 2–4x reduction in per-run CI time is plausible from xdist alone (12 cores), more from selection — *unmeasured here, that's what the spike is for*.

**Build sketch (an agent can do this; Kyle has no step).**
1. **Spike xdist first** (cheapest, largest expected win): run `uv run pytest -q -n 4` and `-n auto` locally against the CI HOME-isolation setup; record pass/fail and time vs. the 775 s baseline. The real risk is not speed but tests that share state (`~/.observer` paths, fixed ports, sqlite files, tmp names) and collide across workers — the spike's output is a list of those, filed as fixes, not a reason to skip. Note the suite's HOME/TMPDIR isolation is per-*job*, so per-worker collisions inside one job are exactly what to look for.
2. If green, add `pytest-xdist` to dev deps (lockfile update via PR per the repo's `--frozen` rule) and `-n auto` to the CI pytest step.
3. **Then** trial `pytest-testmon` on the **PR lane only**, with the persistent `.testmondata` on the runner's disk (the single self-hosted runner makes this easy; it would be awkward on ephemeral hosted runners). Force a full run when the diff touches `pyproject.toml`, `uv.lock`, `conftest.py`, or `.github/**`; keep the full suite on push-to-main as the backstop, so a missed selection is caught within one merge.
4. Measure over a week (per-run minutes, cancelled-run count, and any regression that reached main that selection missed) and report the numbers before widening. Alarm loudly if selection ever runs zero tests.
5. Independent cheap check: confirm why 28% of runs are cancelled (`cancel-in-progress` on rapid re-pushes is probably legitimate; if it's sweeper-driven rebases, that's a separate waste).

**Honest limits.** Anthropic's post is about their scale (25x CI growth); ours is a single runner and ~400 test files, so I am transferring the *principle* (selector + fresh data + backstop), not their service. The speedup numbers for *our* suite are unmeasured. testmon has known rough edges with dynamic imports/subprocess-heavy tests, and this repo has many subprocess/launchd-flavoured tests — the spike should say whether it's viable at all. Not a money/trading change.
