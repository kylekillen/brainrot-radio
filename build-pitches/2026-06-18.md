## PITCH: Compound Loop Signals — Give Your Agent Loops a Shared Brain

**Technique.** Add a structured `signals/` folder to the observer-system that every agent loop both *reads from* before starting work and *writes to* after completing work. A signal is a small markdown file (category, source loop, timestamp, content, linked artifacts) capturing a discovery from one loop that could be useful to another — editorial gaps, breaking story flags, open tasks, friction observed, optimization ideas. Loops that share this signal layer stop operating in silos and start compounding on each other's intelligence across sessions.

**Who's doing it.**
- **AI Jason** — "After spent 30+ hrs building loops..." (June 18 2026): https://www.youtube.com/watch?v=W6x-hb44C0c. Running a production SEO loop for 2 days straight producing 20–40 high-quality pages per day without human intervention. His real company setup: a support loop (every 30 min), an SEO loop (daily), and a product-growth loop — each reading AND writing to the same shared signals folder. When the ad loop finds a keyword with strong CTR but no organic content, it writes a signal; the SEO loop reads it on its next run and prioritizes. That cross-loop awareness is what creates the compounding effect.
- **Boris Cherney (Claude Code lead at Anthropic)** — viral quote, ~700K views on X: "I don't prompt Claude anymore. I write loops, the loops do the work. My job is to write loops." Cole Medin's breakdown: https://www.youtube.com/watch?v=UztrFXaSWv0.
- **Addy Osmani (Google)** — blog post formalizing the pattern: https://addyosmani.com/blog/loop-engineering/. Five primitives: automations (heartbeat), worktrees (parallel isolation), skills (reusable knowledge), connectors (external integration), sub-agents (verification split). Architecture: morning automation → triage skill → isolated worktrees → verification sub-agent → markdown state file.

**Why it matters for Kyle's stack.**
Kyle's setup already has multiple loops: the brainrot-radio launchd pipeline (daily), the COS morning orientation (daily), the PR sweeper (every 5 min), and dispatched workers (reactive). But they're siloed — they don't share discoveries. The podcast pipeline covers a story → the COS doesn't know. A dispatched worker finds an architectural gap → the next dispatched worker in the same repo doesn't see it. The observer-system wiki *compiles* past events passively, but loops don't proactively *write signals* for other loops to pick up.

A signals layer would close that gap: the podcast pipeline would tell the COS what's already been covered; the COS would flag priority topics to the podcast pipeline; workers would leave notes in signals/ that future workers read on briefing. Kyle already has all the infrastructure — the observer-wiki, launchd scheduling, the COS, the dispatcher. The signals folder is the missing connective tissue.

**Build sketch.**
1. Create `~/.observer/wiki/signals/` with a `README.md` defining the schema: one file per signal, frontmatter with `source_loop`, `category` (friction | opportunity | gap | insight | flag), `timestamp`, `summary`, optional `linked_artifacts[]`. Keep the schema simple — 5 fields max.
2. Update `generate-episode.sh` post-publish hook: write a signal with category `covered` listing the top 3 topics, and category `gap` if QC surfaced any notable weaknesses.
3. Update COS morning orientation script to read last 48h signals before planning — one `grep` over `signals/*.md` sorted by timestamp.
4. Update `run_task.sh` dispatcher briefing template to inject signals tagged for the relevant project/domain.
5. Optional compound loop: if brainrot-radio signals a breaking story, the COS loop can create a dispatch task for a research worker without Kyle prompting it.

Implementation cost: low. The signals folder is plain markdown with a light schema. The loop integrations are 5–10 line additions to existing scripts. No new infrastructure required — Kyle already has all the pieces.

**Status: pitched**
