## Pitch 1: Model-tiered orchestration with persistent (cached-context) subagent sessions

**Technique.** Split every non-trivial coding/writing task into three tiers: the
frontier model (Fable 5 / Opus) writes the plan/spec only; a cheap model (Sonnet
5, or an even cheaper external model) executes against the frozen spec; the
frontier model reviews the diff against the spec. Critically, the executor
should be a **persistent, resumable session** — not a fresh one-shot subagent —
so follow-up corrections replay against cached context (~10% the cost of fresh
input tokens) instead of re-paying full context on every correction.

**Who's doing it.**
- AI Jason, "Tmux + Fable = Cut 35% less token" (2026-07, https://www.youtube.com/watch?v=wCSPgHpcxdc) — walks through Claude Code's own recommended coordinator/executor CLAUDE.md pattern, cites Devin's "Fusion" harness (Fable-orchestrator + Sonnet-worker, ~35% cheaper than Fable-only) and explains why persistent "sidekick" sessions beat one-shot subagents specifically because of cached-token pricing. Publishes a copyable CLAUDE.md delegation-rules template.
- Matthew Berman, "You NEED to do this (HUGE AI SAVINGS)" (2026-07, https://www.youtube.com/watch?v=QNEo_tl-nhw) — runs the actual cost math for a plan→execute→review three-stage split: Fable-only ≈ $81/task, GPT-5.6-only ≈ $46.50/task, mixed-model pipeline ≈ $25.55/task for the *same* output. Names the mechanism: output tokens (execution) are the expensive stage and are also the stage a cheap model handles just as well once it has a frozen spec.

**Evidence it's real.** Cross-checked independently — this is not one YouTuber's hunch:
- Anthropic's own published benchmark (via Data Science Dojo and Developers Digest writeups) puts a Fable-5-orchestrator + Sonnet-5-worker setup at **96% of all-Fable performance for 46% of the cost**.
- Multiple independent write-ups (MindStudio, x4 posts; Data Science Dojo; Developers Digest) document the same "advisor/orchestrator strategy" pattern converging on ~10-11% cost reduction at neutral-to-positive quality, corroborating the specific 96%/46% number from a different angle.
- An open-source project (github.com/Nanako0129/pilotfish — "frontier model plans, cheaper models execute, verification guards quality") implements exactly this pattern as installable tooling, i.e. third parties are shipping it, not just discussing it.
- The persistent-subagent mechanism is a real, documented Claude Code feature, not a tmux hack: `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` gates a SendMessage-based resume that reattaches to a subagent's full conversation history (confirmed via code.claude.com/docs/en/sub-agents and independent guides — claudefa.st, developersdigest.tech).

**Need it serves.** Directly answers the open blocker in fleet-optimizer/STATUS.md's 2026-07-20 entry: "the lever named in credit-resilience-plan.md months ago is still unbuilt in the tooling's own defaults... needs a quality-preservation check first." That check now exists — Anthropic's own 96%-performance number — and the plan→execute→review split is itself the quality mechanism (the frontier model owns judgment at both ends; the cheap model only ever executes against an already-frozen spec, which is exactly the shape credit-resilience-plan.md's own "detection is free, only triage costs credits" framing wants). Serves priority 2 (AI-business leverage: this is the multi-agent-without-Kyle unlock, made cheaper) and priority-1-adjacent (burn pressure is what's currently eating into headroom for everything else, including the podcast pipeline itself getting paused during cap weeks).

**Whole-fleet leverage.** This is a Workflow-tool-level default change (or a CLAUDE.md delegation-rules addition to any role's brief), not a single-project fix — it changes the cost profile of every future multi-agent dispatch across observer-system, the COS, and this podcast's own beat-reporter fan-outs, with Anthropic's own number saying quality doesn't measurably degrade.

## Pitch 2: VM-level sandboxing (Docker Sandboxes) for unattended/dispatched agents

**Technique.** Run coding agents that operate with `--dangerously-skip-permissions` inside a per-agent microVM (Docker Sandboxes, GA on macOS as of Jan 2026) rather than directly on the host. The VM — not agent-side prompting — is the security boundary: filesystem access is limited to the mounted project workspace (host `.ssh`, other repos, and the rest of the filesystem are invisible), network egress is allow-listed by domain, and the VM's own nested Docker engine means the agent can't touch host containers. Full cleanup on teardown; an optional `--clone` mode gives a throwaway copy of the repo so even git history/branches can't be touched by mistake.

**Who's doing it.**
- Cole Medin, "How to Actually Run Your Coding Agent Safely (And Avoid the Horror Stories)" (2026-07, https://www.youtube.com/watch?v=zb2LyMro77M) — demonstrates the isolation boundary directly (agent can't read `~/.ssh`, can't reach non-allow-listed URLs, can't touch the host Docker socket) and cites real Claude Code GitHub issues of unsandboxed agents running `rm -rf` on a home directory and wiping a production database mid-debug-session.

**Evidence it's real.** Independently corroborated beyond the (sponsored) video itself:
- Docker's own product blog and product page confirm GA status, the microVM isolation model, and org-wide enforceable network policy (docker.com/blog/docker-sandboxes...).
- At least five independent third-party write-ups in 2026 cover it as a category-defining option, including a comparison piece weighing it against E2B, Firecracker, gVisor, Modal, and Daytona (amux.io), and hands-on "what works, what breaks" reviews (arcade.dev, qovery.com, mintmcp.com) — this is a live, actively-evaluated category, not a single vendor's claim.
- The failure modes it protects against (destructive `rm -rf`, database rollback/migration mistakes, git stash drops, credential exfiltration via prompt injection) are documented, dated GitHub issues against Claude Code itself, not hypothetical.

**Need it serves.** The fleet dispatches a large number of headless/background agents directly on Kyle's Mac (Workflow-tool worker fan-outs, worktree workers, the alarm responder, Fleet-Optimizer-built PRs) — `isolation: 'worktree'` in the Workflow tool protects against *concurrent-write conflicts between agents*, but nothing in the observer-system or Workflow-tool code found in this scan protects against a single agent making a destructive host-level mistake (the exact class STATUS.md's own 07-19 entry already logs once — an uncommitted fix destroyed by a stray `git checkout --` mid-mutation-test). Serves priority 3 (resilience — this is precisely the blast-radius class that would hurt a trading-adjacent process worst) and indirectly priority 1 (a host-level accident is exactly the kind of thing that would consume Kyle's own attention to recover from).

**Whole-fleet leverage.** One VM-runtime addition protects every future unattended/dispatched agent across the fleet at once, rather than patching guardrails per-role; it's also the mechanism-level fix for the class of bug the credit-resilience-plan.md and STATUS.md's own "prompt-only guardrails don't survive context rot" pattern (the T70 arc) keeps re-discovering by hand.

**Build sketch.**
1. Install Docker Sandboxes locally (single command per Cole Medin's video; free) and trial it on one low-stakes, already-headless workload first — the podcast's own beat-reporter/build-pitch dispatch is a reasonable first target since it's non-critical and already runs unattended.
2. Configure the network allow-list to the small set of domains that workload actually needs (RSS/YouTube/API endpoints), confirming host `.ssh` and other repos are invisible from inside the sandbox.
3. If it holds up without breaking the workload, evaluate extending to higher-stakes unattended paths (Fleet-Optimizer's own worktree-worker dispatches, any future PR-fixing worker) — NOT to the trading bots/sentinel themselves without Kyle's sign-off, since that crosses into money-critical infrastructure.

**Status: pitched** (build sketch step 3's extension to trading-adjacent infra is `money — discuss first`; steps 1-2 are safely auto-buildable on a non-critical workload.)
