## PRIMARY PITCH: Tool-Armed External Evaluator

**Technique.** Add a separate, fresh-context evaluator agent to the fleet's worker-completion loop. The evaluator receives the task goal, the GUARDRAILS rubric, and — critically — bash/test tool access to actually run verification commands against the output. It is explicitly prompted to find problems, not approve. This eliminates the self-evaluation trap: workers grading their own work with sycophantic bias and marking mediocre output as done.

This is distinct from T31 (pre-build contract negotiation, shelved by Kyle 2026-06-29). T31 was about negotiating success criteria before building. This pitch is about who does the post-build check and whether they have tools to verify the work rather than just read it.

**Who's doing it.**
- Anthropic's applied AI team (Ash Prabaker & Andrew Wilson), AI Engineer Conference June 2026: https://www.youtube.com/watch?v=mR-WAvEPRwE (77K views) — full workshop demonstrating this pattern in production builds
- The AI Automators breakdown of the same Anthropic blog post: https://www.youtube.com/watch?v=9d5bzxVsocw (180K views)

**Evidence it's real.**
Anthropic used this pattern to build a retro game engine (6 hours, ~$200) and a browser-based digital audio workstation (4 hours, ~$125). The engineers confirmed on stage: WITHOUT the external evaluator using Playwright to actually launch and test the app, the generator declared the game "done" when pressing arrow keys did nothing. WITH the tool-armed evaluator, it worked. Direct quote from Ash Prabaker: "Out the box, Claude is a really, really bad just general QA agent. Most of the time in early runs, it would find a bug and be like, fix it later, might take 2 weeks, and then just be done with it." The evaluator using tools — not just reading diffs — was what changed this.

The engineers gave three specific design requirements: (1) explicit rubric criteria, not vague "is it good?"; (2) tool access so the evaluator can actually run and interact with the output; (3) separate context window from the generator so it can't inherit the generator's rationalizations. They noted that "tuning a standalone critic to be harsh is very tractable, but tuning a builder to be somewhat self-critical is not."

Fleet cross-check: the fleet's current evaluation landscape — GUARDRAILS.md self-grade (worker checks itself), PR reviewer (reads diffs), /goal-bound (worker evaluates its own output) — all have the failure mode Anthropic named: the same agent that did the work is evaluating the work. The fleet has no general-purpose external evaluator with tool access.

**Need it serves.**
Fleet pain: workers completing prematurely or marking mediocre output as done without Kyle catching it. Priority #2 (income — AI businesses; the unlock is multi-agent collaboration that carries work forward without Kyle's constant attention). When workers self-approve bad work, Kyle has to spot-check — which defeats the whole goal.

**Whole-fleet leverage.** Any dispatch producing a verifiable artifact — PR, script, config, skill file — could route through an external evaluator before "done" is declared. First natural target: the delegate skill's completion step. Zero new infrastructure, zero new keys, uses existing Claude on the Max plan.

**Build sketch.**
1. **Add EVAL_RUBRIC sections to GUARDRAILS.md files.** Each role's GUARDRAILS.md gets 4-5 specific, checkable criteria. Not "is the work good?" but specific assertions. Example for a PR: (1) CI green / (2) diff is minimal — only changes required by the task / (3) no GUARDRAILS violations / (4) CHANGELOG updated if behavior changed / (5) tests exist for new logic.
2. **Extend the delegate skill with a post-completion verifier step.** After the worker self-grades GUARDRAILS, spawn a fresh sub-agent with: the task goal (not the worker's reasoning), the GUARDRAILS EVAL_RUBRIC for the role, and bash tool access to run `git diff`, test runner, `wc -w`, lint, or whatever is verifiable. System prompt: "You are a skeptical QA agent. Your job is to find problems. Check each rubric criterion with a specific tool call. Only approve if ALL pass. If any fail, return the exact criterion, the exact command that revealed the failure, and the exact thing to fix."
3. **If evaluator fails: return specific critique to worker, re-dispatch once.** Max 2 evaluator cycles before escalating to Kyle.
4. **Pilot: PR reviewer.** The code-reviewer skill already runs; add a pre-merge evaluator step using the 5-criterion rubric above and `gh pr checks` + `gh diff`. One sprint, low blast radius.

**Cost.** ~$0.15-0.40 per evaluation call. At estimated 5-15 dispatches/day, under $2/day — far less than the cost of Kyle re-checking a bad dispatch.

**Status: pitched**

## Pitch: Ornith-1.0 as the Fleet's Free Local Coding Tier

**Technique.** Ornith-1.0 is an MIT-licensed, self-scaffolding agentic coding model from DeepReinforce (launched June 29, 2026). Four variants: 9B Dense (5.6 GB), 31B Dense, 35B MoE, 397B MoE. All available via Ollama. The defining property is "self-scaffolding" — the model was trained with reinforcement learning to write its own task-specific harness on the fly, then execute against it, rather than relying on a human-authored scaffold. Benchmarks place the 9B at or above models 3× its parameter count on agentic coding tasks. Route non-critical fleet coding worker dispatches to local Ornith-9B for zero credits, zero API key, no new hardware.

**Who's doing it.**
- Sam Witteveen (69k views demo, June 29): https://www.youtube.com/watch?v=uD4-uy0GmHE — tested 35B MoE on multi-step harness generation, tool calls, and constraint adaptation
- "Cloud Codes" (18k views): https://www.youtube.com/watch?v=aKe71FrwL1o — "Ornith 1.0 Is INSANE with Claude Code (FREE + Local + open Source)"
- Simon Willison tested the 35B-Q4_K_M GGUF in LM Studio on a real codebase, June 29: https://simonwillison.net/2026/Jun/29/ornith/
- Ollama official release: https://ollama.com/library/ornith / https://x.com/ollama/status/2070972147686945145
- HuggingFace: https://huggingface.co/deepreinforce-ai/Ornith-1.0-9B

**Evidence it's real.**
- Four independent sources confirmed (Witteveen, Willison, Ollama official, Cloud Codes) with demonstrated outputs
- Ollama ships it as a first-class model tag today — same install friction as pulling any Ollama model
- Willison's review is characteristically critical and specific; he tested against real coding tasks, not toy demos
- 9B is based on Qwen 3.5 with post-training RL — established architecture, not an unknown base
- Fleet cross-check: Ollama IS already installed on this Mac (`/opt/homebrew/bin/ollama`) with `qwen2.5:7b` already running. The infrastructure required is on-disk. Ornith-9B is 5.6 GB — smaller than the already-installed Qwen model (4.7 GB).

**Need it serves.**
Fleet pain: credit/SPOF resilience. Kyle's top-two priorities: income → AI businesses (multi-agent fleet self-sustaining without constant credit top-up). The fleet's credit-resilience plan has two offload paths for the podcast's write burden — both blocked on API keys the fleet doesn't have yet (OpenRouter; Gemini Flash). Meanwhile, non-critical coding worker dispatches (doc updates, skill edits, low-stakes PR fixes, wiki compilation) also drain the Claude credit pool, threatening the money monitor's credit availability whenever a usage surge hits. Ornith-9B unblocks a third path TODAY for that worker-dispatch load: zero cost, zero new account, zero new hardware, reversible in one env var.

**Whole-fleet leverage.** Non-critical coding workers routed to local Ornith-9B = direct credit reduction on the worker-dispatch path, independent of the podcast-offload blocker. Unblocked today. Infrastructure (Ollama, 5.6 GB disk) already present. Rollback is `unset OBSERVER_TASK_RUNNER_CLAUDE` — zero blast radius.

**Build sketch.** Concrete, agent-implementable, no open decisions needed.

1. **Install Ornith**: `ollama pull ornith` (9B, 5.6 GB; Ollama already installed at `/opt/homebrew/bin/ollama`)
2. **Smoke test**: `ollama run ornith "write a bash function that checks if a file exists and returns its line count"` — verify tool-call behavior and output quality for a representative fleet task
3. **Integration hook**: `run_task.sh` line 30 exposes `OBSERVER_TASK_RUNNER_CLAUDE` env var. Default: `claude`. Override: write a thin `~/.observer/scripts/claude-ornith-proxy` shell script that translates incoming `claude -p "$PROMPT" --model ...` calls into `ollama run ornith "$PROMPT"` (or uses the Ollama API endpoint `localhost:11434/v1` via Python). Set `OBSERVER_TASK_RUNNER_CLAUDE=~/.observer/scripts/claude-ornith-proxy` for designated non-critical task types.
4. **Task classification**: Define which dispatch types route to Ornith. Safe: doc/wiki updates, skill edits, low-stakes PR fix, observer-wiki compilation. Must-stay-on-Claude: money-adjacent, QC, build-pitch reporter, alarm triage judgment tail, any dispatch with GUARDRAILS self-grade.
5. **Wire and test**: Dispatch one real observer-system doc-update task through Ornith; verify output before widening the routing rule.
6. **Rollback**: `unset OBSERVER_TASK_RUNNER_CLAUDE` — one line, instant, no state change.

**Adversarial check.**
- *Quality regression?* Real risk for a 9B model — mitigated by scoping Ornith strictly to lowest-stakes dispatches. The 35B MoE would handle more tasks at better quality if the Mac has ~32 GB RAM headroom (current models: gemma3:270m + qwen2.5:7b total ~5 GB, so headroom exists for the 9B and possibly 35B).
- *Integration friction?* The Claude CLI doesn't natively speak to Ollama's endpoint — the proxy wrapper in step 3 is required and needs a 30-minute spike to verify. This is the one non-trivial step.
- *Isn't podcast offload bigger?* Yes — but it's still blocked on an API key. Ornith unblocks a different, currently-accessible path. These are additive, not competing.
- *Self-scaffolding vs fixed harness:* The model generates task-specific scaffolds, which is novel but also less predictable than a hand-authored harness. Lowest-stakes dispatch is the right place to test this property.

**Context: the three-tier model stack frame.** IndyDevDan's June 2026 video ("GLM-5.2 vs MiniMax-M3: Opus Has REAL COMPETITION") articulates the broader pattern: don't pick a model, pick a model stack — state-of-the-art (Claude Opus/Fable) for hardest work, workhorse (GLM-5.2, MiniMax M3 via OpenRouter — still pending key) for heavy non-money tasks, lightweight (Qwen/Gemma/Ornith, local via Ollama) for high-volume low-stakes work. Ornith-9B is the fleet's first buildable step in that lightweight tier — available today, on-hardware, at zero marginal cost. The workhorse tier unlocks once Kyle has the OpenRouter key; the state-of-the-art tier is already in place.
