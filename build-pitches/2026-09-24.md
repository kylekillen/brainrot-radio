## Pitch 1 — Pin and calibrate effort explicitly for Opus 5.5 (the alias flip silently changed the default from `high` to `medium`, and settings-file effort no longer applies)

**Technique.** Opus 5.5 defaults to `medium` effort; Opus 5 defaulted to `high`. Claude Code 2.1.280+ additionally *ignores* the top-level `effortLevel` in settings.json for Opus 5.5 (only `modelSettings."claude-opus-5-5".effort`, `--effort`, or `CLAUDE_CODE_EFFORT_LEVEL` work). Anthropic's own guidance: "set it explicitly, and test several levels against your own evals rather than carrying over the setting you used on Opus 5." Build: a per-task-class effort table for Opus 5.5 that is *measured* on Killen Bench, then passed explicitly at every Claude launch site.

**Who's doing it.**
- Anthropic, "What's new in Claude Opus 5.5" and "Prompting Claude Opus 5.5 → Calibrate effort": https://platform.claude.com/docs/en/models/opus-5-5/whats-new-opus-5-5 and https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5
- Claude Code model-config docs (precedence order, per-model defaults, the "top-level effortLevel doesn't apply to Opus 5.5" note): https://code.claude.com/docs/en/model-config
- Independent builders who hit the same trap and fixed it by passing `--effort` on the command line: basecradle-router #308 (https://github.com/basecradle/basecradle-router/issues/308 — reproduced on CC 2.1.267 and 2.1.280: default session medium, settings ignored, `--effort xhigh` works) and TheVoskamps/claude-config #133 (https://github.com/TheVoskamps/claude-config/issues/133 — "sessions run at medium instead of low").
- Video context: Matthew Berman, "Anthropic went CRAZY (Opus 5.5)" https://www.youtube.com/watch?v=OWu2kjKrRTA (full transcript read; he stresses cost-per-task over price-per-token and that medium beat max on Frontier Code in Anthropic's charts).

**Evidence it's real.** Three layers. (a) Primary docs state the default change and the precedence rule verbatim. (b) Two unrelated GitHub projects reproduced the settings-ignored behavior on shipped CLI versions. (c) Local check: this machine runs 2.1.281; `~/.claude/settings.json` has no effort key, `git grep` in observer-system finds **no** use of `effortLevel`, `modelSettings` or `CLAUDE_CODE_EFFORT_LEVEL`, only 8 `--effort` flags against 27 `--model` launch sites, and `scripts/run_task.sh` (the dispatcher's worker runner) passes no effort at all. So most Claude workers take the model's own default, which changed underneath them on 09-23. **Caveats, stated plainly:** the "medium 5.5 ≥ high Opus 5" and "~40% cheaper per task" numbers are **Anthropic-internal** — TechCrunch and others explicitly note no independent verification, and the 20% list-price cut is the only hard figure (Opus 5.5 $4/$20 vs $5/$25; cache reads $0.20 vs $0.50). Also unconfirmed: whether the router's dial effort reaches claude-backend workers through `run_task.sh` (grep says no; worth one minute to confirm). Killen Bench decision D-07 (09-10) chose external evals over the bench for now, so the sweep needs to be scoped small.

**Need it serves.** Burn / cap pressure (the fourth straight weekly window pinned; Opus 5 was 76% of routed value on 08-29) and Kyle's unresolved default-Opus-vs-too-expensive conflict. Moves priority 2 (fleet runs longer on the same cap, so more work carried without Kyle) and priority 3 (headroom for the trading sentinel's triage). Also a quality hazard: if `medium` is *worse* than the old `high` for reviewer/lead seats, we've silently gone "backwards from current capability", which Kyle ruled out.

**Whole-fleet leverage.** One table, one flag: converts an unmeasured silent default change on ~all Opus workers into a measured, explicit cost/quality setting — plausible double-digit-percent burn reduction (vendor claim, unverified locally) with a quality gate, at the cost of one bench sweep.

**Build sketch.**
1. Confirm the gap (15 min): run `claude -p --model opus --effort low|medium|high --output-format json` on one small task and compare `usage`/duration; confirm `run_task.sh` and the router dial don't pass effort to claude workers.
2. Add `effort` to the router's per-task-class table for family `opus` and thread it through `run_task.sh` / summon as `--effort` (explicit flag wins; don't rely on settings — it's ignored on 5.5). Add `modelSettings."claude-opus-5-5".effort` in `~/.claude/settings.json` as the interactive-session backstop.
3. Small Killen Bench sweep for Opus 5.5 at `low/medium/high` on the 3–4 seats that burn most (code-reviewer, dispatcher workers, COS/leads, summons). Pick the cheapest level that holds pass rate vs the Opus 5 `high` baseline; reserve `xhigh`/`max` for measured gains (Anthropic: 5.5 thinks more per turn at those levels).
4. Add `effort` to the outcome record so burn reports show cost per task class *by effort*.

## Pitch 2 — Early-stop guard for unattended Opus 5.5 runs (measure first, then guard)

**Technique.** Anthropic documents that Opus 5.5 sometimes ends a turn with a text-only progress report (`stop_reason: end_turn`) while work is still owed, and that an unattended loop which treats that as "done" stops early. Their recommended harness fix: treat text-only end of turn as a *report*, keep the task's parts in a checklist file, and if items remain open with no stated blocker, send one continuation message naming them, capped at 2–3 continuations; plus a system-prompt paragraph naming the four unwanted early endings, added at the *start* of a session (adding it mid-session invalidates thinking blocks).

**Who's doing it.** Anthropic, "Prompting Claude Opus 5.5 → Unattended agentic runs" (link above). Three other projects have adopted or queued the same handling: Nanako0129/pilotfish #90 (https://github.com/Nanako0129/pilotfish/issues/90), aganesy/QFAI #2233 (https://github.com/aganesy/QFAI/issues/2233), jl-cmd/claude-dev-env PR #1462 (https://github.com/jl-cmd/claude-dev-env/pull/1462).

**Evidence it's real — and how thin it is.** I read those three: **all are docs-derived proposals, not observed failures.** pilotfish notes two 09-23 runs with matching patterns that still completed. So the only source of the behavior is Anthropic's own guide; nobody has published an incident. That is why this is "measure first": I found **no** early-stop handling in observer-system (`git grep` for premature/early-stop/end_turn guards in `run_task.sh`, summon, coordination: none), so the fleet is exposed if the behavior is real, but I have no fleet evidence that it is happening.

**Need it serves.** Priority 2: headless summons and dispatched workers exist so work proceeds without Kyle; a worker that ends on "next I'll do X" and gets recorded as done is the same false-completion shape as this week's "HANDOFF said armed, wasn't". 

**Whole-fleet leverage.** Cheap insurance on every unattended `claude -p` path against a newly introduced, vendor-documented failure mode; also feeds the stale-state-claims problem.

**Build sketch.**
1. Measurement spike (1–2h, read-only): from `tasks.db`/task transcripts, compare tasks launched before vs after 09-23 (alias flip) for "resolved with no artifact/PR/STATUS entry" or a final message that announces a next step; report a rate.
2. If the rate is non-trivial: in `run_task.sh` and summon, treat a final text-only turn with open checklist items as `incomplete`; one capped continuation ("Your task list still has open items: …"); add Anthropic's unattended-run paragraph via `--append-system-prompt-file` at session start.
3. Keep the human-blocker exception: stops where only Kyle can unblock stay valid.

**Status: pitched** (low-confidence; gate on the measurement in step 1)
