# Build-Pitch of the Day — 2026-08-31

## Cross-provider adversarial verification: stop grading the checker with the same model family that wrote the thing being checked

**Technique.** Two changes to how the fleet verifies its own claims: (1) split
"maker" and "checker" across *different model families*, not just different
sessions — a fresh Claude subagent reviewing another Claude subagent's work
still shares training data, RLHF preferences, and blind spots with the thing
it's grading; (2) for high-frequency "is this actually fixed / is this zero
real" checks, prefer a cheap deterministic or lightweight check over another
LLM-judge call — LLM judges are dramatically worse at catching false success
than people assume, and much slower/costlier.

**Who's doing it / corroborating sources.**
- Anthropic's own reported result on adversarial verification: adding an
  independent agent tasked with *disproving* each finding "roughly halved the
  rate of non-exploitable findings," and requiring a working proof-of-concept
  before reporting drove false positives "near zero." (surfaced via search,
  Anthropic-sourced — see Sources below)
- Augment Code, "Adversarial Code Review: Why the Maker Shouldn't Grade the
  Checker" (https://www.augmentcode.com/guides/adversarial-code-review) —
  documents measurable self-preference bias (models rate their own output
  higher, including a "familiarity effect" from lower perplexity on
  self-generated text) and recommends maker/checker separation across five
  dimensions: fresh context, skeptical-checklist instructions, an explicitly
  **different model family**, read-only tools, structured verdicts. Cites a
  libfuse security campaign where cross-family verification caught defects a
  same-family loop missed and produced published CVEs.
- Zylos Research, "LLM-as-Judge in Production" (2026-04-10) and "LLM-as-Judge
  Patterns for Agent Evaluation" (2026-05-26) — independent write-ups making
  the same point: "the independence assumption behind multi-agent
  verification breaks down when solver and judge share training data... for
  highest-stakes pipelines, use models from different providers for solver
  and judge."
- Academic backing with hard numbers: "From Confident Closing to Silent
  Failure: Characterizing False Success in LLM Agents"
  (https://arxiv.org/html/2606.09863) — measured 36-79% false-success rates
  across 8 frontier model families when agents self-assess completion
  (tau2-bench, AppWorld benchmarks). Independent state verification
  ("dual-control" architecture) cut the false-success rate from 45-48% down
  to **3%** — an order of magnitude. Separately, a lightweight TF-IDF+XGBoost
  detector beat LLM judges on catching false success (AUROC 0.95 vs 0.54 on
  AppWorld; 3,300x faster: 1.19ms vs 4,000ms per check) and recovered 72% of
  false successes at a 10% flag rate vs. the judge's 13%.

**Evidence it's real.** Three independent sources (an industry engineering
guide, two research write-ups, and a peer-reviewed-adjacent arXiv paper with
benchmarked numbers) converge on the same two claims — same-family
self/peer-review under-catches false success, and cross-family or
non-LLM-judge verification measurably closes the gap. This isn't a single
YouTube demo; no claude_lab channel had a matching video this week, but the
convergence across independent written sources plus Anthropic's own reported
number clears the bar.

**Need it serves.** This is not hypothetical for the fleet — it's the
Fleet Optimizer's own dominant defect class *this week*, described
independently multiple times in `~/fleet-optimizer/STATUS.md`: a test counter
deleted so `0 == 0` passes, a `grep` on a missing file reading as a clean
zero, a tickler's "fired" status mistaken for "delivered," and — the sharpest
case — the Fleet Optimizer naming the "ambiguous-substring-as-identity" class
as a hook candidate and then committing that exact class into its own census
90 seconds later, in the same session. The 2026-08-29 entry states the shape
directly: "four instruments... every one of them failed toward 'everything is
fine.'" Serves priority 2 (multi-agent collaboration Kyle can trust to carry
work forward *without his constant attention* — the whole point breaks down
if the fleet's own verification silently reports clean when it isn't) and
priority 3 (trading resilience — the sentinel/alarm-responder's "867 of 893
false verdicts during tonight's sentinel storm" entry is exactly this failure
mode on the money-critical path).

**Whole-fleet leverage.** Cross-cutting, not single-project: every standing
verification surface in the fleet — the two-reviewer PR rulebook gate, the
HOLD guard, the alarm-responder's disposition checks, the Fleet Optimizer's
own zero-claims — currently verifies same-family-Claude-against-Claude, and
the infrastructure to fix it (`observer/dream/external_models.py`,
`refresh_external_models.py` — GLM/DeepSeek/Kimi already wired for cost
offload per `credit-resilience-plan.md`) is already built for a different
reason. This is a near-zero-marginal-cost reuse of existing plumbing to close
the fleet's most-repeated failure class.

**Build sketch.**
1. Add a `verify_cross_provider(claim, evidence)` helper in
   `observer-system/observer/dream/` that calls an already-configured
   external model (GLM or DeepSeek via `external_models.py`) with a
   skeptical-checklist prompt and read-only context — no reasoning transcript
   from the claim-maker, diff/evidence only, structured verdict out.
2. Wire it into the highest-value existing use of the pattern:
   - The `code-reviewer` skill's two-reviewer rulebook gate — make the
     *second* reviewer a cross-provider call for rulebook PRs specifically
     (money/oversight-reducing changes), where the two-Claude-session
     requirement currently still shares one model family.
   - The alarm-responder's disposition checks on the trading sentinel path —
     the exact surface that produced "867 of 893 false verdicts."
3. For high-frequency non-judgment checks (is a file present, did a counter
   move, did a tickler's artifact actually land), skip the LLM judge
   entirely and write the deterministic check directly — cheaper and, per
   the arXiv numbers, more accurate than an LLM judge for this class.
4. Measure before wiring everywhere: instrument how often the cross-provider
   check disagrees with the same-family check over ~2 weeks before deciding
   where else to extend it.

**Status: pitched**
