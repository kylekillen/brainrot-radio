## PITCH: The `/babysit` Loop — CI-Aware PR Shepherd That Runs Continuously Without Kyle

**Technique:** Instead of polling "did it merge?" (which misses the WHY), a `/babysit` slash command runs on a 5-minute loop and shepherds every open PR in the fleet to production: it checks CI status and merge-state, auto-rebases branches that drifted behind main, spawns a small fix worker if CI is red, and auto-merges when green and approved. Kyle's existing `/loop` skill provides the scheduler — `/loop 5m /babysit` is the full invocation. The only missing piece is the `/babysit` skill itself.

**Who's doing it:**
- **Boris Cherny (Creator of Claude Code, Head of Claude Code at Anthropic)** — posted `/loop 5m /babysit` publicly on X (https://x.com/bcherny/status/2038454341884154269) as his own personal workflow, describing: auto-address code review, auto-rebase, shepherd PRs to production.
- **Jökull Sólberg** — published "Babysitting PRs With Claude Code" (https://www.solberg.is/babysit-pr) with a concrete implementation walkthrough, confirming the pattern is practical and reproducible.
- **Matthew Berman** — "7 INSANE loops you need to try right now" (https://www.youtube.com/watch?v=F4a8aMLb678, 96k views) covers the production-error-sweep and nightly loops as the same scheduling primitive, validating the overall loop-as-scheduler pattern. Loop Library at signals.forwardfuture.com/loop-library/ collects 26+ documented loops, confirmed launched on X (https://x.com/MatthewBerman/status/2067682870009925736).
- **Sean Kochel** — "Claude Code Creator: 'Write Loops, Not Prompts'" (https://www.youtube.com/watch?v=EH2MMQTaPEA) cites Cherny's babysit loop specifically, explains the Ralph loop lineage, and names the three cost controls: max iterations, no-progress detection, token ceilings.
- **Official Claude Code Power User Tips** (https://support.claude.com/en/articles/14554000-claude-code-power-user-tips) — Anthropic's own help center lists babysitting PRs as a documented power-user pattern.

**Evidence it's real:**
- Primary source is Claude Code's own creator running this loop personally — not a demo, not a tutorial.
- Official Anthropic help center documents the pattern as a named technique.
- Independent blog post (Sólberg) confirms practical implementation with concrete code.
- Cross-checked against Kyle's existing fleet: the `/loop` skill is already installed; the `/code-reviewer` skill does one-shot PR reviews. The gap is precisely that `/code-reviewer` fires ONCE when a PR opens and doesn't re-engage if CI goes red after the review. The COS ticklers ask "merged?" but not "why not?" — the June 25 STATUS entry is unambiguous: "a deploy/merge-verify tickler must check CI/mergeStateStatus, not just `merged?`, or a red PR rots invisibly behind nag-noise."
- This pitch is distinct from the June 25 Sprint-Contracts pitch (which adds an evaluator loop INSIDE the build cycle). The babysit loop operates AFTER the PR is filed — it's the last-mile driver.

**Need it serves:**
Fleet pain: on June 25 a CI-red PR silently blocked the morning-briefing fix for a full day. The COS fired 20+ ticklers saying "verify #154 merged" but none checked WHY it hadn't — CI had been failing since June 24 with a stale test. The fix was mergeable-but-blocked; nobody saw it. The babysit loop makes that class of failure impossible: every 5 minutes, it inspects `mergeStateStatus` + `statusCheckRollup`, not just `merged?`. If CI is red, it spawns a targeted worker; the PR ships when it's actually ready.

This serves **priority #2 directly** — multi-agent work carrying forward without Kyle's attention. A PR filed by any fleet worker (COS, alarm-responder, podcast pipeline, fleet-optimizer) drives itself to production without Kyle having to notice the red CI or manually merge.

**Whole-fleet leverage:** One 5-minute loop replaces the entire class of "did it merge?" tickler floods with a CI-aware shepherd that drives ANY open PR in ANY repo to completion — a cross-cutting, fleet-wide capability that removes one of the most common failure modes (silent CI failure after PR filing) at near-zero token cost per check.

**Build sketch** (agent-executable, additive — Kyle already has `/loop`):

**Step 1 — Create `.claude/skills/babysit.md`** (~45 min):
```markdown
# Skill: /babysit — CI-Aware PR Shepherd

For each open PR across the active repos (observer-system, brainrot-radio, fleet-optimizer):
1. Run: `gh pr list --repo <owner>/<repo> --json number,title,headRefName,mergeStateStatus,statusCheckRollup,isDraft`
2. For each non-draft PR:
   - **BEHIND main:** `gh pr update-branch --rebase --repo <owner>/<repo> <number>`
   - **CI FAILED:** Spawn a targeted fix: `claude -p "CI is failing on PR #<n> in <repo>. Diagnose and push a minimal fix. Read the failing test output with: gh pr checks <n> --repo <owner>/<repo>." --model claude-opus-4-8`
   - **CI PENDING:** Skip (check next cycle)
   - **CI SUCCESS + MERGEABLE:** `gh pr merge <number> --squash --repo <owner>/<repo>`
   - **BLOCKED (approval needed):** Log to COS queue, skip
3. Run silently unless action was taken — only emit output when something changed.
```

**Step 2 — Wire the loop**:
- In any COS session or observer-system launchd context: `/loop 5m /babysit`
- Or add to `run_task.sh` as a persistent background loop per deploy.

**Step 3 — Token ceiling** (from the Sean Kochel controls):
- The gh status checks are pure CLI — zero tokens.
- Only spawn a fix worker on CI FAILED, which is an infrequent, actionable event. Cap each fix worker at `--max-turns 5` to prevent runaway.
- No token cost for the happy path (CI pending/success/rebase).

**Files to create/modify:**
- `.claude/skills/babysit.md` (new) — the skill implementation above.
- Optionally: wire a nightly run in `~/observer-system/` launchd for always-on operation even when no COS session is active (add a `com.observer.pr-babysit.plist`).
