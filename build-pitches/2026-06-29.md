## Pitch: Pre-Negotiated "Done" Contracts — Generator + Evaluator, Arguing on Disk

### Technique

Before a worker writes a single line of code, a separate evaluator agent (in its own context, with a deliberately harsh system prompt) argues with the worker about what "done" actually means. They write their negotiated contract to a file on disk. The worker builds against that contract, not the original spec. The evaluator then grades against the contract, using real tests — not vibes, not self-assessment.

This is a GAN-style adversarial pattern adapted to agent harnesses: one agent builds, one agent grades, adversarial pressure between them. The key innovation over every current fleet pattern (including /goal-bound delegation and GUARDRAILS.md) is the **pre-build negotiation step** — the evaluator attacks the *done-criteria* before building starts, forcing specificity and catching scope/test weaknesses before they compound over a 3-hour run.

### Evidence It's Real

The workshop shows the same prompt + same model producing two dramatically different results: solo Claude builds a broken retro game (arrow keys do nothing, play mode is fake). The harness builds RetroForge — a named app with a 54-color palette, a working physics loop, and an internal AI assistant the planner added without being asked. Total: ~$200, 6 hours. The evaluator caught real bugs: FastAPI route ordering, Boolean logic in the delete key handler, things that pass unit tests but break in prod. None of it was caught in the solo run. The community implementer hit five of the six failure modes Anthropic described — meaning people are running this enough to hit edge cases.

Key independent verification: the "tuning a standalone critic to be harsh is tractable; tuning a builder to be self-critical is not" claim is structurally sound — it's the same cognitive gap between critique and creation that exists in human organizations, and GAN discriminators have the same property in ML.

### Need It Serves

**Fleet pain (specific):** Workers self-evaluate against vague specs and rationalize success. The 06-28 scan identified self-preferential bias as the unaddressed gap; /goal-bound delegation has the SAME worker evaluate its own output; GUARDRAILS.md is a behavioral checklist but still runs inside the worker's context. None of these use an adversarial external agent whose entire job is to refuse "done" until the criteria are specific and the tests pass.

**Kyle's priority:** #2 — AI businesses, multi-agent collaboration that carries work forward without his attention. The specific failure mode blocking this: a worker declares done, Kyle has to review, discovers it's half-baked, corrects it manually. The generator-evaluator contract eliminates that loop by front-loading the "what does done actually mean?" argument before a single token of build work is spent.

**Difference from the 06-28 adversarial-verification scan:** The 06-28 pattern = N agents independently produce the same output → tournament agent picks winner. Today's pattern = generator and evaluator NEGOTIATE the success criteria before building → evaluator grades against the agreed contract. These are complementary (the 06-28 pattern is best for "what's the right approach?" decisions; today's is best for "did we build what we said we'd build?" — which is almost every dispatch task).

### Whole-Fleet Leverage

One addition to the dispatch template (a pre-build negotiation step where the sub-agent proposes done-criteria and a designated evaluator agent pushes back and signs off) catches the "looks done but isn't" failure class across every high-stakes worker dispatch — without adding new infrastructure, because the fleet already has sub-agents, worktrees, skills, and the PR reviewer as a natural evaluator role.

### Build Sketch

1. **Add a negotiation step to the dispatch template.** Before the worker builds: worker proposes `contract.md` (sprint scope + how to verify it). A separate sub-agent (the evaluator) — different context, harsh system prompt: "Your job is to refuse 'done' until the criteria are specific and testable" — reads the proposal, adds edge cases, rewrites the contract, and pings back. They iterate via the file until the contract stabilizes (no changes in one pass). Then building starts.

2. **Evaluator grades against the contract, not the original brief.** The worker commits. The evaluator runs the agreed verification steps (bash tests / the existing PR reviewer for code tasks; structured output grading for prose tasks). If the evaluator scores below threshold twice on the same criterion → teardown rule: worker starts fresh on that sprint.

3. **State in JSON, contract in markdown.** Consistent with the pattern: `progress.json` (sprint status), `contract.md` (human-readable, writable by both). Don't store sprint status in markdown — workers silently overwrite it.

4. **Natural first pilot:** The /spec-brief dispatch step, already identified in the 06-28 scan as the right pilot target. /spec-brief already produces a machine-readable brief that the evaluator can argue with before the build worker is spawned. Add the negotiation pass between spec-brief output and worker dispatch.

5. **For non-UI tasks:** No Playwright needed. The existing PR reviewer (code tasks) or a structured-output grading agent (prose/analysis tasks) plays the evaluator role. The harness is model-agnostic; the value is the adversarial pressure and the contract file.
