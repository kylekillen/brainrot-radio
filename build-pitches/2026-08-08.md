## Pitch 1 — Split every wiki/memory write into STATE vs. EVENT, and run a periodic audit for drift — closes a gap `SCHEMA.md` itself already flags as unbuilt

**Technique.** Give every piece of information entering a knowledge base (wiki page,
memory file, daily log) one of two types at write time: an **event** (something that
happened — append-only, timestamped, never edited) or a **state** (a current fact —
a rate, a status, a role — which must *overwrite* the previous value, not stack next
to it). Most "second brain" / agent-memory setups default to append-only for
everything, so states silently drift: a core memory file says one number, a daily
log says a newer one, a third document says a third, and the agent has no reliable
way to know which is current — it may pull the stale one. The fix has two parts:
(1) enforce the state/event split going forward, and (2) run a one-time **audit**
skill across the *existing* knowledge base to find and resolve accumulated
contradictions before they keep misleading the agent.

**Who's doing it.**
- Cole Medin, ["Your AI Second Brain Is Slowly Rotting (Here's How to Fix It)"](https://www.youtube.com/watch?v=xOFkpf9KgKg)
  (`claude_lab` feed, Cole Medin channel, this week) — walks through a real failure
  he hit in his own second brain (a client retainer that read $4,000 in his core
  memory file, $6,000 in a daily log, and $9,500 in the actual latest conversation —
  the agent picked the wrong one), then demos a `/second-brain-audit` Claude Code
  skill that scans a knowledge base, flags exactly this kind of drift, and proposes
  (but doesn't auto-apply) state/event splits for human review.
- The skill is a real, inspectable artifact, not just a video demo:
  [github.com/coleam00/second-brain-skills](https://github.com/coleam00/second-brain-skills)
  — "a collection of Claude Skills to turn Claude Code into a Second Brain,"
  installed via two commands, plugin-style. Companion repo
  [coleam00/second-brain-starter](https://github.com/coleam00/second-brain-starter)
  is the same author's broader second-brain scaffold.

**Evidence it's real.**
- Cole Medin's own before/after numbers: his first attempt at fixing this (telling
  the agent to just timestamp everything and reason about recency unassisted) hit
  ~8% compliance in his test set. Only after forcing an explicit state/event
  classification at ingestion did stale-memory pulls drop to "basically never" over
  several weeks of real use — a structural fix, not a prompting tweak, and he
  reports the negative result (the 8% failure) alongside the fix rather than only
  the win.
- The pattern is independently corroborated outside his channel: the broader agent-
  memory literature draws the identical line under different names — "semantic
  memory" (facts updated in place) vs. "episodic memory" (append-only timestamped
  log) — with one production write-up citing zero cross-session contradictions
  across 150+ runs after adopting the same durable-state / event-history split.
  Not one YouTuber's invention; a convergent, load-bearing pattern.
- A comparable third-party "Memory Audit" skill (claudemarketplaces.com) exists
  independently, grading freshness/contradictions across memory stores — further
  sign this is a recognized problem class, not a one-off demo.

**Need it serves.** Category (d), memory & state — the one lane this beat hasn't
covered since the 06-18 reframe. And it's not hypothetical for this fleet:
`~/.observer/wiki/SCHEMA.md` already has a **per-page** current-state/history split
(line 94: "when current state and history conflict, current state wins") and a
conflict-resolution protocol for when a *new incoming event* contradicts a page —
but its own "What v1 does not yet support" section states plainly: **"Cross-page
contradiction detection at scale — v1 handles per-event contradictions only."** That
is exactly the gap Cole Medin's audit skill targets: not the moment a new fact comes
in, but the *accumulated* drift already sitting across dozens of existing pages,
never re-checked against each other. Priority 2 leverage: a COS or Lead operating
unattended off a wiki that's quietly self-contradicting will act on the wrong fact
with no signal anything's wrong — which is the precise failure mode "multi-agent
collaboration that carries work forward without Kyle's constant attention" cannot
tolerate.

**Whole-fleet leverage.** Cross-cutting, not project-specific: applies to
`~/.observer/wiki/` (every role reads it — COS, Fleet Optimizer, every Lead) *and*
to this very session's own auto-memory layer
(`~/.claude/projects/*/memory/*.md` + each `MEMORY.md` index), which has the same
shape (typed memory files, a decay warning already written into the `project` type's
own instructions, no audit mechanism) and the same undetected-drift risk. One
pattern, two knowledge bases, fleet-wide.

**Build sketch.**
1. Pilot the audit on `~/.observer/wiki/` first, read-only: adapt (or install)
   `coleam00/second-brain-skills`' audit skill — or hand its described process to
   an agent directly, since Cole Medin notes the idea itself is simple enough not to
   need the packaged skill — to scan wiki pages + `calibration.md` for cross-page
   numeric/factual contradictions and stale current-state text. Report findings only;
   do not auto-edit (matches this fleet's existing no-silent-money-edits discipline
   and Cole Medin's own design, which stops before writing anything).
2. Have a human (Kyle or a peer role) review the findings once, then decide whether
   to extend `SCHEMA.md`'s conflict-resolution section with an explicit periodic
   audit step — closing the gap its own "what v1 does not yet support" section
   already names, rather than leaving it as a known-but-unaddressed limitation.
3. Separately, run the same read-only audit pass over this session's own
   `~/.claude/projects/-Users-kylekillen-brainrot-radio/memory/` files — small
   surface area, fast to check, same failure mode.
4. If the pilot finds real drift (expect it will — SCHEMA.md's per-event-only
   scoping means it's structurally guaranteed to accumulate over months of daily
   writes), decide on a cadence (weekly, matching the existing
   `queue-accuracy-sweep` pattern) rather than building it as a one-off.
