## Pitch 1 — Google's Open Knowledge Format (OKF) standardizes the exact "LLM wiki" pattern the observer-wiki already is — and completes a namespace the wiki's own spec deferred and never built

**Technique.** OKF v0.1 is an open, vendor-neutral specification for representing an AI agent's curated knowledge as a directory of markdown files with YAML frontmatter — `index.md` files for hierarchical/theme navigation, concept/entity files linked into a graph, optional `log.md` for chronological history. No new runtime, no required SDK, no compression scheme — just files and a small set of conventions, designed specifically so a wiki written by one producer can be consumed by a different agent without translation.

**Who's doing it.** Cole Medin, ["The Ultimate Knowledge Base: Bring YouTube Into Your AI Second Brain"](https://www.youtube.com/watch?v=8JWhwhxWtJw) (2026, claude_lab beat) — builds an OKF-formatted 200-video knowledge bundle for his own YouTube channel and demonstrates an agent answering multi-video synthesis questions with cited sources and timestamps, faster and cheaper than re-reading transcripts. He frames it as a direct successor to Andrej Karpathy's April 2026 "LLM-maintained personal wiki" gist — the same pattern Kyle's own `~/.observer/wiki` implements.

**Evidence it's real.** Verified beyond the single video:
- Primary source: [Google Cloud's own blog post](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing), published 2026-06-12 by Data Cloud tech leads Sam McVeety and Amir Hormati, with the spec itself on GitHub ([GoogleCloudPlatform/knowledge-catalog/tree/main/okf](https://github.com/GoogleCloudPlatform/knowledge-catalog/tree/main/okf)) under Apache 2.0, plus a reference enrichment agent and a static HTML graph visualizer.
- Independently corroborated by at least six separate trade-press writeups with matching details (publish date, authors, structure): [MarkTechPost](https://www.marktechpost.com/2026/06/16/google-cloud-introduces-open-knowledge-format-okf-a-vendor-neutral-markdown-spec-for-giving-ai-agents-curated-context/), [Search Engine Journal](https://www.searchenginejournal.com/google-cloud-announces-the-open-knowledge-format/579253/), [TechTimes](https://www.techtimes.com/articles/318416/20260615/google-cloud-open-knowledge-format-turns-scattered-org-knowledge-agent-ready-bundles.htm), [MindStudio](https://www.mindstudio.ai/blog/what-is-open-knowledge-format-okf-google-llm-wiki-standard), [explainx.ai](https://explainx.ai/blog/google-open-knowledge-format-okf-ai-agents-2026), and an OKF-specific resources hub ([openknowledgeformat.academy](https://openknowledgeformat.academy/resources/)).
- Adoption signal, not just a vendor announcement: Karpathy's original pattern (April 2026) had 200+ independent implementations before Google's spec even shipped — OKF is standardizing something already organically adopted, the same shape as MCP standardizing the agent-to-tool pattern a year earlier.
- I directly compared the spec against `~/.observer/wiki/SCHEMA.md` (Kyle's own wiki spec): it's a near-identical convergent design — markdown pages, YAML frontmatter, an index/log layer, cross-linked pages. The wiki's own SCHEMA.md (line 307) explicitly reserves `concepts/` and `patterns/` namespaces for "v1.x" and states "What v1 does not yet support" for exactly that layer — a planned, scoped, never-built piece of the wiki's own roadmap that OKF's concept/entity index would satisfy off the shelf.

**Need it serves.** Memory & state optimization (this beat's dimension d) plus a real, freshly-observed instance of the retrieval-cost problem: this session's own `~/fleet-optimizer/STATUS.md` read hit a hard 25,000-token truncation on a 91,000-token, 1017-line flat log with no structured index — forcing either an expensive multi-page read or blind grepping to avoid missing the right section. Serves priority 2 (the multi-agent unlock): a standardized, agent-agnostic knowledge format is exactly what "delegated work carrying forward without Kyle's constant attention" needs at the memory layer — any future agent or OKF-aware tool can consume the wiki or a role's log without bespoke re-learning of a private schema. Indirectly serves priority 1: every role that currently re-derives context by reading a growing flat file is spending tokens (and, transitively, some of the fleet's scarce weekly cap) on retrieval instead of work, which is exactly the kind of friction-removal that protects Kyle's attention.

**Whole-fleet leverage.** Not project-specific — this is a memory-layer standard applicable to `~/.observer/wiki` (the fleet's shared biographical memory, read by every role) and, as a pilot, to `~/fleet-optimizer/STATUS.md` itself, whose own append-only growth pattern is the one that got hit this session. A working index/concepts layer on either file makes every future reader's retrieval cheaper and more precise, not just this one lookup.

**Build sketch.**
1. Read the OKF v0.1 spec directly from the GitHub repo (small, no SDK) and diff its `index.md`/concept-file schema against `~/.observer/wiki/SCHEMA.md`'s existing page types — most of the shape already matches (frontmatter, cross-links, log.md); the gap is specifically the `concepts/`/`patterns/`/themed-index layer SCHEMA.md already reserved but deferred.
2. Pilot small: generate an OKF-style `index.md` (themes + concept/entity links) for one already-large, already-painful file first — `~/fleet-optimizer/STATUS.md` is the concrete, freshly-observed candidate, since its lack of an index is what caused this session's truncation. Use Google's own reference "enrichment agent" pattern (or a simple Claude-authored equivalent) to generate the index from the existing markdown rather than hand-writing it.
3. Test before rolling further: have a fresh agent answer a real "what's the state of X" question using only the OKF index + targeted file reads, compare token cost and accuracy against today's full/partial-read approach.
4. If the pilot holds, extend the same index layer to `~/.observer/wiki` itself, completing the `concepts/`/`patterns/` namespace SCHEMA.md already scoped — treating OKF as the external spec that fills an internally-planned gap rather than a foreign migration.
