## Pitch 1 — Tier the fleet's dispatched workers by *effort × model*, measured on cost per landed task

**Technique.** Claude's `effort` setting (low / medium / high / xhigh / max) is now the main cost-and-quality dial, and Anthropic's own guidance is to sweep it per workload, then use a "run at low, re-run failures at higher effort" ladder instead of one setting for everything. With Opus 5.5 (released 2026-09-22, $4/$20 per Mtok, default effort `medium`), Anthropic claims Opus 5.5 at `low` often beats Sonnet 5 at default on agentic tasks *per solved task*, even though the per-token price is higher. The fleet has never run this sweep: its dispatched workers run at each model's default effort.

**Who's doing it.**
- Anthropic, ["Optimizing for cost and intelligence — tune effort"](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence): Opus 5.5 on SWE-bench Pro, `medium` ≈ 70% of `high` cost for ~2.5 pts less; `low` ≈ 33% of cost for ~8 pts less; "low first, re-run failures at high" ≈ 97% pass at ~$0.17/task vs 95.3% at $0.29 all-high. On research/knowledge work (Fable 5.1) `low` gave up 1-3 pts for a third to a half off cost; `medium` matched default at 70-87% of cost.
- Matthew Berman, ["Anthropic went CRAZY (Opus 5.5)"](https://www.youtube.com/watch?v=OWu2kjKrRTA) (2026-09-23, with an Anthropic Claude Code lead): shows Frontier Code medium effort under $1/task scoring above max effort at $5+/task. Transcript pulled and read.
- Independent: [Artificial Analysis, Opus 5.5 release page](https://artificialanalysis.ai/models/releases/claude-opus-5-5): Intelligence Index low 42 / medium 51 / high 54 / xhigh 56 / max 58, cost per task from $0.55 (low) to $5.98 (max). Sonnet 5 scores 38 and Fable 5.1 53 on the same index. The fleet's own `model-landscape.md` already carries the Opus 5.5 medium/high/xhigh/max rows.
- Academic: [arXiv 2608.01347, "Prompt-Induced Waste in Coding Agents: Reasoning, Effort, Harness Design, and End-to-End Cost"](https://arxiv.org/abs/2608.01347): effort "may improve performance on complex tasks but can also add cost without benefit," and the right metric is cost per successful task. Only the abstract was read.

**Evidence it's real.** Three independent-ish sources agree the effort curve is steep at the low end and flat at the top (Anthropic docs, Artificial Analysis, the arXiv paper). Caveats, so nobody overstates this:
- The Anthropic numbers are vendor-run and cover Opus 5.5 and Fable 5.1. I found **no published effort curve for Sonnet 5**, the model that carries most of this fleet.
- The benchmarks are SWE-bench Pro and research tasks. The fleet's biggest lane is PR review, which none of them measure. So this is a strong hypothesis, not a proven saving, and the build sketch starts with measurement.
- "Opus 5.5 low beats Sonnet 5 default per solved task" is Anthropic's claim. The independent index says only that Opus 5.5 low (42) out-scores Sonnet 5 (38); it doesn't settle cost.

**Not already built (checked).** `run_task.sh` (the dispatched-worker runner) passes `--model` but no `--effort`. The only `--effort` in the fleet is `medium` on the observer compile steps (`observer_heartbeat.sh`, `cli.py`). The words "effort" and "Opus 5.5 worker" appear in no Fleet Optimizer slate item, `burn-control-plan-2026-08-29.md`, or `burn-allocation-policy.md`. The existing routing work (`external-model-routing.md`, `model-router`) picks *which model* by availability and cost band, not *how hard the model thinks*, and the fallback chain is about outages, not tiering. This differs from the rate-limit / multi-provider idea rejected on 09-27: that spreads work across providers, this tunes spend inside the Anthropic pool.

**Need it serves.** Credit and burn pain (`credit-resilience-plan.md`, `burn-control-plan-2026-08-29.md`): the shared metered pool is what starved the alarm responder and the podcast in June. Serves priority 2 (multi-agent work carrying itself, cheaper per landed PR) and priority 3 (headroom for the trading sentinel's judgment lane). Priority 1 indirectly: fewer review cycles means less waiting and fewer stalls on Kyle's attention.

**Measured baseline from the fleet's own task DB (`~/.observer/data/tasks.db`, last 14 days, `cost_usd` is ccusage-equivalent, not cash):**
- About $1,380 of tracked cost across all tasks.
- `claude-sonnet-5` 579 tasks / $515 (avg $1.02), `sonnet` alias 337 / $227, `claude-haiku-4-5` 532 / $197, `claude-opus-5` 107 / $255 (avg $5.20), `claude-opus-5-5` 37 / $81 (avg $4.50), Fable 27 / $81.
- Sonnet-family workers are roughly 54% of tracked cost; PR-review tasks alone are about 900 tasks (456 on sonnet-5 at $0.57, 440 on haiku at $0.40).
- Code-quality table (`model-landscape.md`): claude-sonnet-5 authoring PRs average 1.47 review cycles and 78% first-pass approval, so a real share of spend is re-runs that a better first attempt would avoid.

**Whole-fleet leverage.** One config knob applied to ~1,900 tasks per 14 days could take a double-digit percentage off the ~$740 Sonnet bucket and cut review cycles, without touching any provider or trading logic. The size of the saving is unknown until measured. For scale only: a 20% cut of that bucket would be about $150 per 14 days.

**Build sketch (an agent can start with no further context).**
1. Read-only first: add `effort` and `attempted effort` to the task record. Have `run_task.sh` record the effort it launched with (`claude --effort <level>` exists in the installed CLI). Nothing changes behaviour yet.
2. Pick two lanes with clean outcome data: `pr_review` (score by later CHANGES_REQUESTED or reversed verdicts) and PR-authoring workers (score by review cycles to merge, from `model_code_quality.py`). Use the existing shadow-review machinery (`shadow_review_sweeper.py`) so no live gate changes.
3. Shadow sweep on a sample of ~50 tasks per arm: Sonnet 5 default vs Sonnet 5 medium vs Opus 5.5 low vs Opus 5.5 medium. Metric is cost per *landed* task (including re-review cycles), not per token, as Anthropic and the arXiv paper both recommend.
4. If a cheaper arm holds quality, set the default via the existing `OBSERVER_TASK_DEFAULT_MODEL` precedence plus a new `OBSERVER_TASK_EFFORT`, and add the "low first, escalate to high on a failed check" ladder inside the pr-sweeper retry path.
5. Guardrails: any direct-API code moved to `claude-opus-5-5` must drop `thinking: disabled` and forced `tool_choice` (both now 400 errors), and must check `stop_reason: "refusal"` (HTTP 200, empty content). Check that `deniedModels` / `availableModelsMatch` settings, new in Claude Code 2.1.283, don't block the aliases the runner passes. Keep money-lane routing unchanged: Kyle's 09-03 ruling puts money lanes in the router, so any effort change there goes through the router, not around it.
