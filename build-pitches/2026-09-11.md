## The find — and full disclosure: this is a resurfaced pitch, not a new one
**Technique.** Docker Sandboxes: run coding agents in `--dangerously-skip-permissions` ("Yolo") mode inside a per-agent microVM instead of directly on the host. Each sandbox gets its own kernel, filesystem, network stack, and nested Docker engine; the host filesystem outside the mounted workspace is invisible to the agent (verified in the video: `.ssh` is unreachable from inside the sandbox), outbound network is default-deny with an explicit per-domain allowlist (`sbx policy allow network`), and `--clone` mode gives the agent a full isolated copy of the repo so it can't touch git state on the host at all. One command to install, one command to run (`sbx run claude`).

**I am not presenting this as new.** This exact technique was already pitched by this beat twice — `build-pitches/2026-07-24.md` and `2026-07-25.md` — justified by two failure classes: (a) a Claude Code bug where resumed background agents silently lost their permission restrictions, and (b) subagents in isolated git worktrees being able to redirect Git operations into the shared parent checkout. The 2026-07-31 follow-up pitch (`build-pitches/2026-07-31.md`) verified that Claude Code 2.1.216 closed **both** of those specific holes natively, and said plainly: *"the sandboxing pitch's remaining justification narrows to host filesystem/credential access and network egress — still real, but Kyle should know the goalposts moved before deciding whether the VM-level investment is still worth it."* Nobody decided. The Fleet Optimizer's own later review (`~/.observer/wiki/agent-os/fleet-optimizer-runs.md`, line 293) flagged that the item "isn't in any queue you read... exists only inside dated pitch files" — six weeks of sitting unqueued and undecided.
